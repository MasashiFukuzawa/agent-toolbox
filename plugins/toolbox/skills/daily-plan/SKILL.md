# Daily Plan — 今回やることの合意と進捗

これから最大24時間でやる作業を人と合意し、その期間の進捗を1枚のHTMLで追う。ページは計画1つにつき1枚で、期間が終わったら次の計画で新しいページを作る。
開いた人が「期間の目標にどこまで近づいたか」「いま何が進み、何で止まっているか」「次の一手は何か」を聞き返さずに分かる状態を保つ。

ページは同梱の `scripts/render.py` が計画JSONから書き出す。状態の判定と完了率の計算をスクリプトに任せ、HTMLを手で書き換えない。手で書くと遅いうえに、数字と手順の状態がずれる。

## 役割分担

| スキル | 担当 |
|---|---|
| daily-plan | 今回の作業・手順・タイムラインの合意、計画JSON、進捗ページの描画と定期更新、持ち越し |
| progress-report | 目的・マイルストーン・現在地の材料。単発の報告はこちらで作り、計画ページを報告の代わりにしない |
| owner-board | 人への判断依頼・作業依頼と回答の記録。計画ページには依頼の中身を書かず、Q番号でリンクする |
| html-artifact | 見た目（DESIGN.md）と保存先の規則。結論ブロックとAsIs/ToBe図は計画ページでは使わず、本スキルの画面構成に従う |
| autopilot | 実行の委任・権限・判断待ちの扱い。計画の合意は委任の範囲を広げない |

**計画への合意は、merge・apply・本番のJob実行・外部への送信などの操作の承認ではない。** 承認が要る操作は、計画に入っていても、その操作の直前に対象・環境・影響を示して個別に承認を取る。計画に書く手順名にも「（承認後）」のように承認が要ることを残す。

人が不在の間（夜間など）に承認が要る操作まで進めたいときは、合意のときに操作ごとの対象・実行してよい条件・中止する条件・失敗や結果不明のときの回収方法と回収操作の許可・期限を示し、その操作に限った事前承認を明示的にもらう。「全部やっていいよ」のような包括的な言葉は事前承認とみなさず、操作ごとの条件を示して確かめ直す。事前承認の無い操作は直前で止め、owner-boardに依頼を書いて手順を待ちにする（連絡板が無ければチャットで頼む）。操作の対象（どの環境の何を変えるか）を材料から特定できなければ、推測で埋めず「要確認」として聞く。人のレビューが要るPRは待ちとして扱い、AIが代わりにapproveしない。

## 期間とファイル

- 期間は `start` と `end`（タイムゾーン付きの日時）で決め、24時間以内にする。朝から夜、夜から翌朝のどちらでもよい。日をまたぐ計画を2つに割らない。
- 保存先はhtml-artifactの「保存先」に従い、`<project>/YYYY-MM-DD_daily-plan_<slug>/` を作る（日付は最初の計画を作った日、`<slug>` は取り組み全体の名前）。同じ取り組みの間は同じdirectoryを使い続ける。作る前に既存のdirectoryを探す。

| ファイル | 寿命 | 中身 |
|---|---|---|
| `goals.json` | 取り組みの間ずっと | 段階の並び、目標ごとの到達済みの段階と期限までの目標段階、元の計画へのリンク |
| `YYYY-MM-DD_HHMM.json` | 計画1つ | 名前は計画の開始日時。作業・手順・予定と実績の時刻・待ち・時間制約・計画の変更 |
| `YYYY-MM-DD_HHMM.html` | 計画1つ | 描画結果。期間が終わったページは残すが、描画し直さない |

項目の書き方は [データ形式](references/data-format.md) を読む。出発点は `assets/example/` の2ファイル（夜から翌朝までの架空の計画）。コピーして、架空の内容をすべて実際の内容に置き換える。

## 1. 下書き

次の材料から計画を下書きする。材料に無い作業・期限・数字を創作しない。

1. `goals.json`。無ければ、親Issue・マイルストーンなどの正本から段階と目標を作る。正本が見つからなければ目標の段は省き、無いことをチャットで伝える。
2. 前回の計画JSONの未完了の手順。持ち越すものは、持ち越す理由（「外部の公開待ちが続いている」など）を `note` に書く。やめるものは、やめる理由をチャットで伝える。理由の無い持ち越しと黙った削除をしない。前回の計画で起動した監視などの処理が今も動いているかを確かめ、結果を `note` に書く。止まっていれば、合意後に起動し直すか、`check` を外して手で確かめるかを決めてチャットで伝える。前回の計画が締められていなくても、前回のファイルは書き換えない。
3. owner-boardの連絡板があれば、回答済みで計画に効くQと、回答待ちで手順を止めているQ。止まっている手順には `ref` にQ番号を書く。
4. GitHubなどで確かめられる現状（PRの状態、CI、実行結果）。確かめた手順には `check` を付け、自動で判定させる。外部の公開などを監視する処理を起動するときは、そのコマンドを手順の `note` に残し、次の計画で起動し直せるようにする。

作業（lane）ごとに、何が満たされれば終わりかを `goal` に1行で書き、どの目標のどの段階を進めるかを `advances` で結ぶ。当てはまる目標が無い作業（保守など）は `advances` を省き、目標外であることと入れる理由をチャットで伝える。目標を作り足さない。頼まれた作業が期限の目標を越える、または途中の段階を飛ばすときは、`advances` には実際に進む段階を書き、飛ばす段階とそのリスクを合意のときに確かめる。手順は「何をするか」が名前だけで分かる粒度にし、1つの作業に3〜8個を目安にする。

期間の長さから入りきる量を見積もる。入りきらなければ、期限の目標を左右する作業を残し、外した作業を「今回は扱わない」としてチャットで示す。待ち（外部の公開、レビュー、人の回答）と、守る時間制約（例：本番停止を避ける時間帯）はタイムラインに置く。

## 2. 合意

1. 計画JSONを保存し、`python3 <このスキルのdirectory>/scripts/render.py <計画JSON>` で描画する。終了コードが1なら、標準エラーの理由を直して描画し直す。
2. チャットに次だけを出し、合意を求める。
   - 期間（開始〜終わり、日をまたぐなら日付も）
   - 作業ごとに1行：名前・進める目標と段階・予定の時刻
   - 持ち越したものと理由、外したものと理由
   - 期間中に承認が要る操作（合意とは別に、その時点で承認を取ると明記する。人が不在の間に進めるものは、上の事前承認の条件も示す）
   - ページのパス
3. 修正を受けたらJSONを直して描画し直す。合意を得るまで作業に入らない。
4. 合意したら、計画の終わりまで描画を繰り返す処理をバックグラウンドで起動する。

   ```sh
   python3 <このスキルのdirectory>/scripts/render.py <計画JSON> --watch 10
   ```

   10分ごとに描画し直し、計画の終わりを過ぎたら最後に1回描画して自分で止まる。ホストのバックグラウンド実行（Claude CodeならBashのバックグラウンド実行）を使い、起動したことと止め方をチャットで伝える。途中でJSONが壊れても止まらず、直れば次の回で描画される。ページは、開いている人が読んでいる途中には差し替えず、タブが裏にある間か前面に戻ったときに、5分より古ければ読み込み直す。

## 3. 期間中の更新

描画はバックグラウンドの処理に任せ、計画JSONだけを書き換える。HTMLは手で書かない。

- `check` で判定できない手順は、状態が変わったときに `state` と `note` を書き換える。状態は `done`（完了）・`doing`（進行中）・`waiting`（待ち）・`blocked`（止まっている）・`todo`（未着手）の5つに限る。
- 人の報告で状態が分かったとき（「CIが通った」「公開された」）は、`check` で確かめられればそれに任せる。確かめられなければ `check` を外し、`state` と `note`（誰の報告か・何時か）に書く。後の変更でやり直しになりうる完了（CIなど）は、再確認の条件も `note` に書く。監視の出力ファイルを手で作って判定を通さない。
- 作業を始めた・終えたら、その作業の `actual` に時刻を書く。途中で別の作業に切り替えたら、`actual` を区間の配列にして中断した時刻で閉じ、手順を `todo` に戻す。`plan` は再開後の区間に置き換え、元の予定と再開の時刻を `changes` に書く。再開したら `actual` に区間を足す。時刻を言われなければ、指示を受けた時刻を使い、そう決めたことを返答で伝える。
- 計画を変えたら（順番の入れ替え、作業の追加・取りやめ、時刻のずれ）、`changes` に時刻と理由を1行で足す。手順や予定を黙って書き換えない。
- 人の判断待ちで止まったら、依頼はowner-boardに書き、計画JSONには `ref` でQ番号だけを書く。依頼の背景・選択肢・推奨を計画ページに書かない。回答が来たら `ref` を外し、`note` には「Q14 回答済み」のように番号だけを書く。決まった中身はowner-boardを正本にする。
- 期間中に大きく計画が変わり、合意した前提（期間・主な作業）が崩れたら、変更を足すだけで済ませず、チャットで再合意を取る。

`--watch` を使わない場合や処理が止まっていた場合は、更新のたびに `render.py` を1回実行する。「計画ページを最新化して」と頼まれたら、JSONを現状に合わせてから1回描画する。

## 4. 締め

期間の終わり、または予定の作業がすべて終わったとき：

1. 手順の状態と `actual` を最終の状態にし、描画する。期間の終わりより前に締めたら、古い状態で描き直されないよう `--watch` の処理を止める。終わった後なら、止まったことを確かめる。
2. 期限の目標に向けて進んだ段階があれば `goals.json` の `reached` を更新する。根拠（merge済みのPR、受入の記録など）が無い段階は進めない。
3. チャットに、終わったこと・終わらなかったことと理由・次の計画へ持ち越す候補を短く返す。次の計画の下書きは、頼まれたときに1から始める。

## 画面の構成

`render.py` が次の順で描く。構成を変えたいときはスクリプトを直し、出力したHTMLを手で直さない。

開いてすぐ「いま何が進み、何で止まっているか」が見えるよう、今回の進捗を先頭に、取り組み全体の目標を最後に置く。

1. **見出し**：タイトル（既定は期間）、更新時刻とタイムゾーン、計画の終わりまでの残り時間、元の計画と連絡板へのリンク。
2. **作業の進捗**：全体の完了率と状態別の内訳、作業ごとの要約表（完了率・内訳・手順数・次の一手）。次の一手は、作業の中で最初の未完了の手順とその理由。
3. **タイムライン**：期間の時刻軸に、作業ごとの予定（点線）と実績（塗り）、待ち、守る時間制約（斜線）、現在時刻の縦線を描く。日をまたぐ軸は0時に日付を添える。下に計画の変更を並べる。
4. **作業ごとの手順**：作業ごとに、終わりの条件と手順の一覧。
5. **期間の目標**：目標ごとに段階を並べ、到達済み（済）・いま・期限までの残り・対象外を塗り分ける。期限の目標の段階に◆、今回の作業が進める段階に▲を付け、作業へリンクする。

状態は5つで固定し、どれも色と文字の両方で示す。色はDESIGN.mdの3系統に合わせ、完了と進行中を青、待ちと止まっているを橙、未着手を灰にする。

## 出す前の確認

- 計画の期間が `start`・`end` と一致し、日をまたぐ計画で日付が正しく出ているか。
- 前回からの持ち越しすべてに理由があるか。外した作業をチャットで伝えたか。
- 承認が要る操作を、合意とは別に承認を取る手順として書いたか。人が不在の間に進める操作に、操作ごとの事前承認と中止の条件があるか。
- 計画ページに依頼の中身や機密（認証情報・顧客データ）を書いていないか。Q番号のリンクだけか。
- `check` のPR番号・run ID・`repo` が実在するものか。判定できないときに手動の `state` が正しい既定になっているか。
- 描画の終了コードが0で、`--watch` の処理を起動した（または起動しない理由を伝えた）か。
