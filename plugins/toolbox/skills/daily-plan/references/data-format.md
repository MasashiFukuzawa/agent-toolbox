# データ形式

`render.py` が読む2つのJSONの項目。例は `assets/example/` にある。必須でない項目は省いてよい。

## goals.json（取り組みの間ずっと使う）

| 項目 | 必須 | 中身 |
|---|---|---|
| `title` | | 見出し（例「4月の目標」）。既定は「期間の目標」 |
| `periodEnd` | | 目標の期限。表示するだけ |
| `stages` | ○ | 段階の名前を進む順に並べる。既定の例は `["契約・設計", "実装", "staging受入", "本番受入"]` |
| `source` | | 元の計画へのリンク `{"label": "...", "href": "https://..."}` |
| `goals[]` | ○ | 目標の一覧 |
| `goals[].id` | ○ | 計画JSONの `advances.goal` から参照する英数字のID |
| `goals[].name` | ○ | 目標の名前 |
| `goals[].reached` | ○ | 到達済みの最後の段階。まだ何も済んでいなければ `null` |
| `goals[].target` | ○ | 期限までに到達したい段階 |
| `goals[].note` | | 目標の下に出す1行（例「配信先の決定待ち」） |

`reached` と `target` は `stages` にある名前にする。無い名前は描画エラーになる。

## 計画JSON `YYYY-MM-DD_HHMM.json`（計画1つ）

| 項目 | 必須 | 中身 |
|---|---|---|
| `start` / `end` | ○ | タイムゾーン付きのISO 8601の日時（例 `2026-04-14T20:00:00+09:00`）。`end` は `start` より後で、24時間以内 |
| `title` | | 見出し。既定は期間（例「4/14 20:00〜4/15 08:00 の作業」） |
| `goals` | | 計画JSONから見た `goals.json` の相対パス。省くと期間の目標の段を出さない |
| `repo` | | `check` でGitHubを見るときの `owner/name` |
| `ownerBoard` | | 連絡板へのリンク。`ref` のQ番号は `<ownerBoard>#<Q番号>` へのリンクになる |
| `source` | | 合意した計画の元（会話のメモ・Issueなど）へのリンク `{"label", "href"}` |
| `refreshSeconds` | | ページが古くなったとみなす秒数。既定は300、0で読み込み直さない。読んでいる途中は差し替えず、タブが裏にある間か、前面に戻ったときに読み込み直す |
| `lanes[]` | ○ | 作業の一覧。上から優先順に並べる |
| `constraints[]` | | 守る時間制約 `{"start": "HH:MM", "end": "HH:MM", "label": "何を守るか"}`。見出しの下に文字で出す |
| `changes[]` | | 計画の変更 `{"at": "HH:MM", "text": "何をなぜ変えたか"}` |

リンク（`href`・`ownerBoard`）は `https:` か相対パスだけを使う。それ以外はリンクにせず文字だけ出す。

### lanes[]（作業）

| 項目 | 必須 | 中身 |
|---|---|---|
| `name` | ○ | 作業名 |
| `goal` | | 何が満たされれば終わりかを1行で |
| `advances` | | 進める目標と段階 `{"goal": "<goals[].id>", "stage": "<stages の名前>"}` |
| `steps[]` | ○ | 手順。1つ以上 |

### steps[]（手順）

| 項目 | 中身 |
|---|---|
| `label` | 手順名（必須） |
| `state` | 手動の状態。`done`・`doing`・`waiting`・`blocked`・`todo` |
| `note` | 状態の理由や結果を短く |
| `check` | 自動判定（下表） |
| `waitLabel` | 自動判定で「待ち」になったときに出す理由。`note` があれば後ろに続けて出す |
| `ref` | 止めている依頼のQ番号（英数字とハイフン）。連絡板へのリンクになる |

状態は `check` → `state` → `todo` の順に決まる。`check` で判定できない（GitHubに届かない、PRがまだopen など）ときは `state` を使うので、`check` を付けた手順にも、判定できないときの状態を `state` に書いておく。

| `check` | 判定 |
|---|---|
| `pr-merged:<番号>` | mergeで完了、mergeされずに閉じたら止まっている。openの間は `waitLabel` があれば待ち、無ければ `state`（無ければ進行中） |
| `pr-closed:<番号>` | 閉じたら（merge含む）完了 |
| `pr-ci:<番号>` | 全部成功で完了、失敗ありで止まっている、実行中で進行中 |
| `run-success:<run ID>` | 成功で完了、実行中で進行中、それ以外の結論で止まっている |
| `file-nonempty:<path>` | ファイルが空でなければ完了（最後の行を注記に出す）。空か無ければ待ち。外部の公開を監視する処理の出力などに使う。相対パスは計画JSONから見た位置 |

GitHubの判定は `gh` を使う。`repo` が無いときは判定せず `state` を使う。

`file-nonempty` は、ファイルが空か無ければ `state` を見ずに待ちになる。人の報告などで完了が分かったときは、監視の出力ファイルを手で作らず、`check` を外して `state` と `note`（誰の報告か、何時か）に書く。

## 守る時間制約と計画の変更

`constraints[]` は、期間中に守る時間帯を書く（例 `{"start": "06:00", "end": "09:00", "label": "本番停止を避ける"}`）。ページには「本番停止を避ける 06:00–09:00」のように文字で出る。取り組みの間ずっと守る制約は、次の計画へ引き継ぐ。終わりが分からない制約は、計画の終わりの時刻を `end` にし、`label` に「終わり未確認」と書く。

`changes[]` の `at` は、変更した時刻をそのまま書く。

## 描かなくなった項目

タイムラインは描かない。そのためだけに使っていた `lanes[].plan`（予定の時刻）、`lanes[].actual`（実績の時刻）、`waits[]`（外部要因の待ち）は読み飛ばすので、書かなくてよい。以前の計画JSONに残っていても、そのまま描画できる。待ちは、手順の `state`・`waitLabel`・`note` に書く。

## 入力が不正なとき

`render.py` は理由を標準エラーに出して終了コード1で終わり、既存のHTMLを書き換えない。`--watch` 中は止まらずに次の回で読み直す。
