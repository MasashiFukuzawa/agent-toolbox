# HTML Artifact — 見て分かる一枚物

人が見て理解するための資料を作る。本質は、次の3つを読み手が追加のやり取りなしで受け取れるようにすること。

- **論点**：何についての話で、何が問題か
- **理解してほしいこと**：何がどう変わるか、どんなリスクがあるか
- **合意・決定してほしいこと**：何を、どの推奨と理由で、いつまでに決めてほしいか。決めた後に何が起きるか

迷ったら読みやすさを優先する。理解にも判断にも効かない情報はノイズとして削る。総論から各論へ降りる順に書き、図で語り、文章は補うだけにする。

## 先に決めること

- 誰が読み、何をしてもらう資料か（判断・相談・共有）を一行で定め、HTML冒頭のコメントに残す。判断が変わる不明点だけ尋ねる。
- 論点を書き出す。決めてほしいこと・理解してほしいことを箇条書きにして番号を振る。これが資料の骨格になり、結論ブロックの実施事項と本文の節はこの番号に対応させる。
- 総論のスコープが、一度の議論で合意できる大きさかを判断する。次のどれかに当たれば大きすぎる。外部の期限があるもの、他の決定の前提になるものを優先し、1つの推奨と目的でまとまる範囲だけを残して1つの資料にする（当てはまる論点が1つだけならそれだけでよい）。外した範囲は、タイトル直下に「今回は扱わない」と外した理由を添えて1行で示す。外した範囲の資料を作るかはチャットで確認する。依頼が全範囲や細部の網羅を求めていても、この判断を優先する。
  - 論点が4つ以上ある
  - 互いに独立した決定が混ざり、1つの推奨や目的でまとめられない
  - 前提（方針・目的）の合意がないまま、細部を決めてもらおうとしている（先に前提を論点にする）
  - 総論の粒度に抽象化しても、AsIs/ToBe図が1枚に収まらない、または変わる箇所が多すぎて強調が効かない

  逆に小さすぎて全体の中の位置が見えない場合は、総論で全体と今回の範囲の関係を示す。論点は読み手が1回で答えられる（共有のみなら理解できる）単位にし、同じ読み手に同じ種類の影響を与える小さな話題は1つの論点に束ねてよい。ただし読み手が一部だけ別案を出しうるものは束ねない。上の「4つ以上」は束ねた後の数で判定する。
- 読み手が返信の前に聞き返しそうな質問を先に挙げる（「なぜ別案ではないのか」「失敗したら戻せるか」「自分の作業は何か」など）。答えは資料に入れ、資料の外で補足しなくて済むようにする。
- `progress-report --html` からの連携では、整理済みの事実・基準時点・判断材料を使い、内容選択はprogress-reportに任せる。HTML化のついでに対象を広げない。
- 人への依頼と回答を継続更新する連絡板はowner-boardの規則に従う。

## 最初の画面：結論とAsIs/ToBe

デスクトップ（1280×800程度）の最初の画面に、タイトル・結論ブロック・重大なリスクを必ず収め、AsIs/ToBe図も主要部（両側の見出しと、番号を付けた変わる箇所）まで見えるようにする（図の高さは320px程度に抑える）。収まらないときは、カードの余白などDESIGN.mdの値は変えず、結論ブロックの文言を削る。

- **タイトル**: 題材を短い名詞句で書く（例「認証基盤の移行」）。副題・キャッチコピー・飾りのメタ情報は付けない。
- **結論ブロック**: 「課題／目的／実施事項」の3行。資料の中で最も読まれる場所なので、一言一句を詰めて書く（次節）。
  - 依頼がなければ実施事項は「なし（共有のみ）」とし、続けて理解してほしいことを1文で書く。この1文は論点の要旨だけにし、課題やリスクの行と同じ事実を繰り返さない。
  - 重大なリスクと、推奨を覆す条件は結論ブロックのすぐ下に1行ずつ示す。折りたたまない。無ければ行ごと置かない。
- **AsIs/ToBe図**: 結論の直後に置き、総論を図で示す。現状と目指す姿を並べ、変わる箇所だけを色・印・ラベルで強調する。変わる箇所には論点の番号を付け、各論の節が図のどこを詳しくするのかを示す。承認や起票のように図の要素に対応しない論点は、AsIsからToBeへの矢印に番号を付ける。完了済みなどで変化の無い論点は、該当する要素に番号を付けて「変化なし」と書く。細部は描き込まず、総論の粒度に留める。題材に合わせて構造・流れ・数値・利用者の体験のどれで対比するかを選ぶ。箱を2つ並べただけの図にしない。進捗報告では「現在地 → 完了状態」と読み替える。変化を扱わない題材（仕組みの説明など）に限って省略し、代わりに論点の番号を付けた全体像の図（流れ・構造など）を置く。
- 「3秒で」カード、KPI帯、判定バーなど、結論を言い換えて繰り返す区画は置かない。

### 結論ブロックの書き方

各行は、読み手がその行で抱く問いに、その行だけで答える。経緯や作業名の言い換えで終わらせない。

| 行 | 読み手の問い | 書くこと |
|---|---|---|
| 課題 | なぜ今この話で、放っておくと何が困るのか | きっかけになった事実・変化と、誰に・何が・どれだけ起きるか。数字・時期・固有名詞で。読み手が知らない前提があれば、必要な分だけここに含める |
| 目的 | 何が満たされれば終わりか | 完了を確かめられる状態や基準。「〜な構成にする」のような方向だけで終えない |
| 実施事項 | 自分は何をすればよいか | 論点の番号ごとに、決めてほしい対象、推奨とその決め手（1つ）、期限、回答後に起きること。読み手の手作業があればそれも番号を振り、推奨と決め手の代わりに作業内容を書く |

- 決め手は、推奨案だけが持ち他案に無い理由を1つ選ぶ。残りの理由は比較の図に回す。
- 共有のみの資料では、課題に「基準時点で終わっていないこと・待っているもの・遅れたときの影響」を書く。推奨が無いので、推奨を覆す条件の行は作らない。
- 課題に書いた影響と、結論ブロック直下のリスクの行で同じことを二度書かない。リスクの行に回すなら、課題は待っているものまでで止める。
- 「背景」の行は作らない。背景と課題に分けると、同じ事実を言い換えて二度書きやすい。
- 1行（実施事項は1件）は1〜2文、80字程度までにする。短くするために情報を抜かず、言い換え・前置き・重複を削って密度を上げる。
- 実施事項は表にせず、番号ごとに1〜2文の行で書く。2件以上なら、最後に回答の仕方を1行添える（例「番号ごとに ok／別案 で返信」）。全件に共通する期限はこの行にまとめ、各行で繰り返さない。
- 「整理」「対応」「改善」「検討」「最適化」「方針」のような中身のない語で文を終えない。何をどう変えるかに置き換える。
- 数字・期日・条件は入力にあるものだけを使う。推定は「推定」と書く。
- 書くべき項目（期限、推奨を覆す条件、完了時期、比較表の欄など）が入力に無いときも作らない。入力から導けるもの（既にあるリスクの裏返し、外部の期限からの逆算など）は導いたと分かるように書く。導けなければ「未定」「未確認」と書き、何が足りないかをチャットで伝える（例：所要期間が分からず外部期限から逆算できないなら「回答期限は未定（所要期間が未見積もり）、是正期限は3月末」）。
- 書き終えたら1行ずつ「だから何？」と問い、答えが行内に無ければ書き直す。続けて1語ずつ、消しても意味が変わらない語を削り、曖昧な語を具体に置き換える。

| | 薄い | 詰めた |
|---|---|---|
| 課題 | CIの移行先が未定 | 3か月でCIが12分→25分に伸び、1日のmerge数は30件→18件に減った。runnerは並列4本が上限で、来四半期に40分超（推定） |
| 目的 | 安定したCI構成にする | merge前のCIを10分以内に戻し、並列数を設定変更だけで増やせる状態にする |
| 実施事項 | 移行先を決める | 移行先を案A（マネージドrunner、月$400増）で承認してほしい。決め手は運用作業ゼロ。11/20までの回答で月内に切替 |

## 総論から各論へ

読み手は全体像と前提を掴んでから細部を読む。いきなり各論が来ると、前提が伝わらず書き直しになる。

- 順序は「タイトル → 結論ブロック（総論：課題・目的・決めること）→ AsIs/ToBe図（全体像）→ 各論の節（論点の番号順）」に固定する。
- 各論で使う前提・用語・比較の軸は、総論か各節の冒頭で先に示す。設定値・コマンド・個別ファイルのような細部から節を始めない。
- 各論の見出しには論点の番号を付け、AsIs/ToBe図で同じ番号を付けた箇所を詳しくする節だと分かるようにする。
- 各論でも、その論点の中身が変化そのものなら、総論の図の該当箇所を拡大した細かい粒度のAsIs/ToBe図を置いてよい。1つの資料に粒度の違うAsIs/ToBe図が複数あるのは自然なことで、「同じ形式の繰り返し」とは扱わない。総論の図と同じ要素名・色・論点の番号を使い、総論の図のどこを拡大したものかが分かるようにする。総論の図と食い違う内容は描かない。新しく作る仕組みのように現状に対応するものが無ければ、ToBe側だけの拡大図でよい。
- 総論に無い論点を各論で持ち出さない。必要なら総論に戻って論点に加えるか、スコープ外として削る。

## 図で語る

- 本文の節は論点の番号に対応させ、その論点を理解・判断するのに要るものだけを置く。どの論点にも効かない節は作らない。
- 1つの節は「主張を書いた見出し1行＋図1つ」を基本にする。見出しは「待ち時間の8割はレビュー待ち」のように結論を書き、「現状分析」のような分類名にしない。本文の段落は原則書かない。
- 図の形式は、伝える関係から毎回選ぶ。同じページで同じ形式を繰り返していないか確認する。箱と矢印は、実際にある流れや依存を示すときだけ使う。

| 伝える関係 | 形式の例 |
|---|---|
| 変化・前後 | 前後の並置、差分のハイライト、スロープチャート |
| 選択肢の比較 | 推奨列を強調した比較表、2×2マトリクス、並列の棒 |
| 量・割合・余裕 | 棒、積み上げ帯、アイコン配列、ゲージ、区間付きのドット |
| 時間・順序 | タイムライン、ガント帯、担当別レーン |
| 構造・包含 | 入れ子、層、ツリー、配置図 |
| 流れ・依存 | フロー図、シーケンス図、分岐 |
| 担当・状態の対応 | マトリクス、ヒートマップ |
| 画面や物の位置関係 | 簡略化した画面・配置のスケッチ |

- 図のラベルは語句にする。長い文章を図の中へ移すだけにしない。
- 図で使う記号・色・略称は、図のそばの凡例で先に示す。
- 数字には単位・時点・母数を付ける。事実／推定／不明を区別して示す。見栄えのために数値や日程を作らない。期間が確定していない工程を、確定した長さで描かない。

## 説明は隠す

- 隠すのは、判断には不要だが確かめたい人がいる根拠だけ。調査の経緯・作業ログ・今回の論点と無関係な事項は、隠さずに削る（伝える必要があればチャットで伝える）。
- 補足は開かなくても読めなくてよいものだけにし、次の方法で隠す。
  - 用語・一言補足：ラベル横の「?」ボタン。hoverとfocusで表示し、Escで閉じられるようにする。
  - 根拠・前提・詳細：`<details>`。summaryには「比較の前提を見る」のように中身が分かるラベルを付ける。
- 結論・重大なリスク・期限・推奨を覆す条件、読み手の手作業は隠さない。

## 見た目と文言

- 見た目は [references/DESIGN.md](references/DESIGN.md) に従う。HTMLを書き始める前に読み、末尾のCSSトークンをそのまま使う。
- デスクトップ幅だけを想定する。スマホ向けのレイアウトやmedia queryは作らない。幅が足りない図は、その図の領域だけ横スクロールにする。
- ライトテーマだけを作る。`color-scheme: light` を指定し、ダークテーマや切替UIは作らない。
- 配色は色覚の多様性に配慮する。赤と緑の対比で意味を分けない。意味を持たせる色はDESIGN.mdの3系統に絞り、色に加えて文字・アイコン・形でも意味を伝える。
- 本文は16px、図中の文字は12px以上にする。
- 文言は語句と体言止めを中心にし、同じことを二度書かない。「〜について説明します」のような前置きや締めの要約は書かない。

## 自己完結・安全・アクセシビリティ

- 1ファイルにinline CSS・最小限のJS・inline SVGで作る。doctype、`lang`、UTF-8、`<title>` を付ける。外部CDN・外部フォント・fetch・外部iframeは、明示要件がない限り使わない。
- 機密情報・個人情報を埋め込む前に共有範囲を確認する。secretや認証情報は含めない。
- table・th（scope付き）・button・details/summaryなど、ネイティブ要素を使う。focusを見えるようにし、「?」やdetailsをキーボードで開けるようにする。
- SVGには `role="img"` とaccessible nameを付け、図の要点は見出しの文字でも伝える。
- WCAG準拠と断言しない。

## 実装の落とし穴

コードだけで確認するので、表示崩れの原因になりやすい次の点を作る段階で避ける。

- SVGの文字幅は、全角1文字をfont-size、半角1文字をfont-sizeの0.6倍として見積もる。箱の幅は「文字幅＋左右16px以上」にする。収まらなければ箱を広げるか、`<tspan>` で改行する。線のラベルは線から離し、背景を敷く。
- SVGは `viewBox` と `width:100%` で可変幅にする。縮小すると図中の文字が12px未満になる場合は、縮めずに横スクロールにする。
- 複数のSVGで使うmarker・gradientのidは図ごとに一意にし、すべての `url(#…)` が解決することを確認する。SVG内の `<style>` も文書全体に効くので、共通スタイルはページの `<style>` に置く。
- 日本語を含む要素に `text-transform: uppercase` を、日本語の文章幅に `ch` 単位を使わない。
- `overflow:hidden` やline-clampで文字を切らない。ツールチップが親要素のoverflowやページの端で切れないようにする。

## セルフレビューしてすぐ開く

ブラウザでの表示確認は行わない（ユーザーから頼まれた場合は、browser-operationsを読んでから行う）。保存後にコードを読み返し、次を確認・修正する。

1. 結論ブロックの各行が「結論ブロックの書き方」を満たすか。1行ずつ読み直し、読み手の問いに答えていない行・中身のない語を直す。
2. 総論だけで全体像と決めることが分かり、各論が総論のどの論点を詳しくしているか分かるか。総論のスコープが一度の議論で合意できる大きさか。
3. 読み手として通読し、返信の前に聞き返したくなる点が残っていないか。残っていれば答えを資料に足す。逆に、消しても理解と判断が変わらない要素は消す。
4. 最初の画面にタイトル・結論ブロック・重大なリスクが収まり、AsIs/ToBe図の主要部が見えるか（要素の高さを足して見積もる）。
5. 数値・根拠・結論と図の内容が一致しているか。プレースホルダやサンプルが残っていないか。
6. DESIGN.mdのDon'tsと、上の「実装の落とし穴」に当たる箇所がないか。
7. 隠した補足を開かなくても、判断に必要なことが分かるか。

修正後は、保存した最終版をすぐOSの標準の方法で開く。macOSは `open "<絶対パス>"`、Linuxは `xdg-open "<絶対パス>"`、Windows PowerShellは `Invoke-Item -LiteralPath '<絶対パス>'` を使う。ユーザーが開かないよう指定した場合は従う。開けなかった場合は、その理由を報告する。

保存先の優先順位は、ユーザーの指定 → repoが定めるartifactの慣習 → repo外のsession成果物領域。他者の作業ツリーへ副産物を混ぜない。

チャットには結論1〜2行とHTMLの絶対パスを返し、「表示はコードのセルフレビューのみで確認」と一言添える。HTML全文・行数・自賛は書かない。
