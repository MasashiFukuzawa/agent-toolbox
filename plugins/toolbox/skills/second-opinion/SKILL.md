# Second Opinion — 第三者に確かめさせる

現セッションの文脈・前提・思い込みを共有しない別プロセスに、成果物を確かめさせる。価値はモデルの強さではなく独立性にある。Claude Code・Codex・Cursor のどのホストからも、シェルで相手のCLIを起動して使う（ホストがCodexならClaudeを、ホストがClaude CodeならCodexを呼べる。同じproviderの別インスタンスも呼べる）。

## 使う場面

- 対象は、後から誤りが分かったときの手戻りが大きい成果物に絞る。設計メモ・提案書・ADR・アーキテクチャ判断・リリース前のコード・セキュリティ境界が当たる。
- 型チェック・lint・テストで検出できる欠陥は、案件の検査のコマンドが担う。呼び出し元がすでに結論を持ち、同意だけを求める確認にも使わない。
- 対象外だと判断したら、見立てと代替案（型チェック・lint・テストの実行、その場での目視確認）を述べ、実行するかの判断を依頼者へ返す。判断を任されたセッション（autopilotではゴールを進めるセッション）は自分で判断する。ユーザーが承知の上で求めたら実行する。

## 2つのやり方

| やり方 | 第三者がすること | 権限 |
|---|---|---|
| 動作確認 | 固定した写しの上で実際に動かし、受入条件を1つずつ確かめる | 写しの中だけ書き込める |
| レビュー | 差分・設計を読み、指定された観点で、失敗する場面を挙げる | read-only |

- 振る舞いが外から見える変更で、案件の「任せる範囲」が第三者の確認を求めるとき（「深い確認が要る変更」に当たる）は、動作確認を先に行い、その結果をレビューの材料として渡す。
- それ以外はレビューだけを行う。受入条件のすべてを実装者のテストで確かめられる変更では、実装者の「変更前に落ち、変更後に通る」証拠で足りるので、動作確認を省く。

## ガードレール

1. **provider**: 明示された名前に従う。Claude・Anthropic・Sonnet・Opus・Fable を挙げた依頼はClaude、Codex・OpenAI・sol・astra を挙げた依頼はCodexを起動する。providerが未指定で、選択権限も委任されていなければ、どちらを使うか確認する。選択を任されたセッションは`model-selection`と任せる範囲で選ぶ。
2. **権限**: レビューはread-only、動作確認は写しの中だけ書き込める形で起動する。起動コマンドは [Claude](references/claude.md) / [Codex](references/codex.md) の形をそのまま使い、権限を定める引数が欠けたコマンドを実行しない。終了後に`git status`で作業ツリーの汚染を確かめ、汚染があればすぐ報告する。
3. **ネスト起動の禁止**: 起動した第三者に、別の`claude -p`・`codex exec`・review系スキルを起動させない。依頼文に再帰防止文を必ず入れる。
4. **外部への書き込みの禁止**: commit・push・PR作成・コメント・Issueの作成や更新をさせない。動作確認でも本体のコードは直させず、不合格は報告として返させる。
5. **明示指定の尊重**: ユーザーがモデルやeffortを明示したら、自動判定で上げも下げもしない。明示指定とは、モデルのfamily名・ティア名（モデルIDや版付きの名前を含む）か、effortのレベル名（`low`・`medium`・`high`など）を挙げたものを指す。「しっかり」「念のため」「軽く」は明示指定ではなく、依頼の複雑さの手がかりとして扱う。
6. **40分で判断を返す**: 開始時に、対象の規模と実測に基づく所要時間の見込みを伝える。実時刻で40分たっても完了していなければ、状況を報告し、「続ける」か「中断してもう一方のproviderへ切り替える」かを判断者に示す（任されていれば、ゴールを進めるセッションが決める。中断時は結果の部分回収を試みる）。基準は「出力が無い」ではなく「完了していない」である。処理中に出力が無いのは常態で、それだけでは失敗の根拠にならない。
7. **上位の実行制約**: ホストや現在の会話に課された実行制約を、このスキルやCLIの起動で迂回しない。使えないときは、スキルの規則によるのか実行環境によるのかを分けて説明する。side sessionという名前だけを理由に、第三者の起動を禁止はしない。

## モデルとeffort

選ぶ前に、同じtoolbox pluginの`model-selection`スキルとそのモデル表を読む。モデルID・effort・昇格の基準はそこだけで定め、このスキルには複製しない。未導入なら不足を報告し、古い既定値を推測しない。確定した値を、起動前に`REVIEW_MODEL`と`REVIEW_EFFORT`へ設定する。

結果の質が足りないときは、対象と観点を具体的にし、`model-selection`に従ってモデルを見直す。質を補う独立した再レビューは新しいsessionで行い、同じ処理の回収・追加質問は正確なsession IDで継続する。

## 依頼文

ユーザーの依頼を、意図を保ったまま次の5つを含む指示にする。会話から分かることは確認せず、分からないことだけ確認する。

1. **再帰防止文**（先頭に置く）。

   ```text
   You are the reviewer. Inspect the repository directly.
   Do not invoke second-opinion or any review skill, codex exec, claude -p, or any nested reviewer.
   Return findings directly as text.
   ```

2. **対象と範囲**。全体・特定のファイルやdirectory・差分のどれかを言い切る。差分は、未コミット（ステージ済み・未ステージ・untrackedのどれを含むか。既定は3つとも）、ブランチ差分（作業ツリーの未コミット分を含めるか。既定は含める）、特定のcommitを区別する。写しで起動したときは、写しのHEADが「元のHEADの上に、作業ツリーの現在の状態を載せた1コミット」になることを前提に範囲を伝える。未コミットの変更は`HEAD~1..HEAD`、ブランチ差分は`<base>...HEAD`（未コミット分を含めないなら`<base>...HEAD~1`）、特定のcommitはそのSHAである。`.gitignore`されたファイルは含まれないと添える。
3. **確かめる基準**。依頼の原文、受入条件、設計の該当箇所を、引用するか場所で渡す。repoの規約を定める文書（AGENTS.md・CONTRIBUTING・ADRなど）の場所も渡す。基準が言葉になっていなければ、先に依頼者と受入条件を言葉にする。
4. **観点**。次の4つを渡す。依頼に固有の懸念（権限の境界、並行実行、データ移行など）があれば、心配している失敗の形を具体的に書き足す。

   | 観点 | 挙げるもの | 根拠 |
   |---|---|---|
   | 欠け | 依頼・受入条件が求めているのに、無い、または一部しか無いもの | 該当する要件の引用 |
   | 頼まれていない | 依頼に無い振る舞い・機構・設定・抽象 | それが動く場面と、依頼に無い結果 |
   | 実装違い | 実装や設計はあるが、要件どおりにならない場面 | 該当する要件の引用 |
   | 規約違反 | 文書化されたrepoの規約への違反（ツールが強制しているものは除く） | 規約のファイルと該当箇所 |

   文書のレビューでは、契約の定義・manifest・package設定など対象の実装を列挙し、文書の現在形の記述と突き合わせさせる。
5. **返す形式**。次をそのまま入れる。

   ```text
   次の形式で、全体を1,500字以内で返してください。
   ## 指摘（外したときの損害が大きい順）
   各指摘は5行以内で、次をすべて書く。1つでも書けないものは「未検証の懸念」へ回す。
   - 観点: 欠け / 頼まれていない / 実装違い / 規約違反
   - 根拠: 該当する要件または規約の引用
   - 場所: path:line
   - 失敗シナリオ: 具体的な入力や状態と、そのとき起きる誤った結果（規約違反は、違反箇所と規約の引用で足りる）
   ## 未検証の懸念（最大3件、各1行）
   ## 検査しなかった範囲
   今回見ていないファイル・観点・前提。
   字数に収まらない指摘は、損害の大きい順に書いたうえで、残りの件数だけを末尾に書く。
   命名や文言の好み、将来の拡張に備える提案、型チェック・lint・テストで検出できるものは書かない。
   ```

観点と基準を渡すのは、基準の無い「厳しく見て」という依頼が、命名や将来の拡張についての指摘を増やすからである。

## 動作確認

レビューの依頼文の1〜3に加えて、次を渡す。

- **受入条件**: 番号を振り、合否を外から判定できる形で書く。
- **動かし方**: 依存の導入、起動、実行のコマンド。必要な環境変数は名前と入手方法を書き、値は依頼文に書かない。
- **返す形式**:

  ```text
  ## 動作確認
  受入条件ごとに、合格 / 不合格 / 確かめられず、実行したコマンド、終了コード、出力の要点を書く。不合格には再現手順を付ける。
  ## 確かめられなかったことと理由
  コードは直さず、見つけた不具合は報告だけにしてください。
  ```

進め方は次のとおり。

- 写しは [スナップショットの作り方](references/review-snapshot.md) で作ったworktreeを使い、それを作業rootにして起動する。`.gitignore`されたファイル（導入済みの依存、ローカル設定）は写しに無いので、依存の導入は写しの中で行わせる。
- 依存を導入できない、認証が要るなどで環境を立ち上げられないときは、粘らせずに「確かめられず」と理由を返させる。時間の上限はガードレール6に従う。
- ログインが要るstagingやtest環境での確認は、`e2e-capability-verification`の手順（認証の引き継ぎ、破壊的な操作のガードレール）に従う。認証情報を依頼文で第三者へ渡さない。
- 結果は、続くレビューの依頼文へ「動作確認の結果」として貼り、不合格になった受入条件の原因を「実装違い」の観点で見させる。

## 起動と合流

起動コマンドは [Claude](references/claude.md) / [Codex](references/codex.md) にある。コマンドは単独で直接実行せず、[実行記録](references/durable-run-record.md) を作るwrapperの内側で実行する。起動ごとに新しいrun UUIDを作り、ホストの永続state root配下の`reviews/<run_uuid>/`を専用のrun directoryにして、起動前にrun UUIDと絶対pathをユーザーへ伝える。一時directoryやrepoの中には置かず、別のrunのdirectoryやファイルを再利用しない。

処理は数分から数十分かかりうる。出力が無い間も推論は続いているので、長いことを理由にkill・キャンセル・再実行をしない。**呼び出し元を解放する形で起動し、合流はホストの機構に任せる。** 起動直後に、所要時間の見込みと、応答が無くても処理は続いていることを伝える。

| 型 | ホストが持つ機構 | 起動 | 合流 |
|---|---|---|---|
| 通知型 | 完了を通知する背景実行（例: Claude Codeの背景実行） | 背景実行で起動する | 完了時にホストがエージェントを再び呼ぶ |
| ハンドル型 | 待ち時間の上限とセッションハンドルを持つコマンド実行（例: Codexのコマンド実行ツール） | 短い待ち時間で起動し、ハンドルを保持して制御を取り戻す | 自分からハンドルを読みに行く |
| 同期型 | どちらも無い | foregroundで実行する | 戻り値をそのまま受け取る |

- **通知型**: 通知を主な経路にし、60秒を目安に、ホストが持つタスクの終了状態と未処理の通知を軽く照合する。大きな途中ログを繰り返し読まない。
- **ハンドル型**: 起動時に次の確認期限を記録し、60秒以内の短いread/waitで制御を戻して照合する。放置すると永久に合流しない。ハンドルと出力先は控えておき、推測したハンドルやpathを読まない。
- **同期型**: 待ち時間が無いので、予告は実行の直前に出す。ホストの実行タイムアウトに収まらないときは、繰り返し実行せず、対象を絞るかeffortを一段下げる（明示指定があれば、下げてよいかユーザーに確認する）。
- 経過時間は実時刻の差で測り、起点は起動の成功を確かめた時刻にする。反復回数と待ち時間の掛け算で数えない。`sleep`と再読込を組み合わせた自作のポーリングはせず、ホストが提供するブロッキングのwait/readを使う。
- 完了通知は実際の終了より先に届くことがある。CLIが出す完了の印かプロセスの終了を確かめてから結果を回収する。どちらも確かめられないホストでは、ホストが返す最終結果と終了ステータスを根拠にする。
- `nohup`・`setsid`によるシェルレベルのdetachは使わない。ホストの機構が無ければ同期型として扱う。
- 合流したら、人間による停止と安全上の異常を最優先し、次に結果の検証と報告を行う。autopilotの利用時は、止まり方と引き継ぎの決まりにも従い、実行中の処理をゴールのページの「引き継ぎの情報」に書く。

### 待ち時間に進める作業

待ち時間に対象のrepoを触る予定があれば、写しで起動する。写しは実ツリーとindexに触れず、untrackedを含む現在の状態を固定する。この場合、ガードレール2の汚染の確認は写しのworktreeで行う。

写しを取らずに起動したら、完了まで次の3つを変えない。

1. 対象のツリーとindex（編集、commit、stash、branchの切替、依存の更新）。
2. 依頼が参照するref（`git fetch`・`git pull`）。
3. 共有の`.git/config`とhooks。worktreeの追加は`git -c core.hooksPath=/dev/null worktree add`で、起動より前に済ませる。

待ち時間に何を進めるかは制限しない。対象に依存する変更のmergeは、結果を処理した後にする。サブエージェントへ任せるときは、上の制約と再帰起動の禁止をそのまま伝える。

### 中断・回収失敗からの復旧

会話の割り込みや合流の失敗を、第三者の処理の失敗と同じに扱わない。sessionが成立した後の割り込みでは、次の順で復旧し、新しい起動を先にしない。CLIが依頼文を受理する前に終了し、process・出力・sessionのmetadataのどれからも成立を確かめられないなら、起動の失敗である。原因を直して新しく起動する。事前に採番したIDだけでは成立の証拠にならない。

1. 伝えてあるrun UUIDから`record.json`を開き、状態と、記録したprocess identityを確かめる。`running`でidentityが一致するprocessが生きていれば、記録したハンドル（同期型ならその結果）で待って回収し、同じsessionへ同時にresumeしない。processが無い、またはidentityが一致しなければ、終了済みとしてevent・stderr・終了ステータスを確かめる。記録を開けず状態を確定できなければ、process名・更新時刻・候補のsessionから推測せず、resumeも新規起動もせずにユーザーへ報告する。
2. 終了済みなら、記録した出力先かホストの最終結果から、既存の出力を先に回収する。依頼文が求めた終わりの要素（少なくとも結論と「検査しなかった範囲」）が欠けていれば未完了とする。回収できない、または未完了のときだけ、記録した正確なsession IDでresumeして同じ処理を完了させる。
3. session IDを安全に特定できなければ、推測したIDや「直近のsession」を選ぶ引数で別のsessionへつながない。復旧できないことと、新しく起動すると時間とトークンを再び使い、元の探索の文脈も引き継げないことを報告して、判断を返す。

resumeは、記録した作業rootから、元のモデル・effort・対象・権限を保って行う。写しで起動していたら同じ写しを使い、新しい観点や範囲を足さない。resumeがsession不存在で失敗したら繰り返さず、3へ進む。resumeと追加質問のコマンドはproviderごとの参照ファイルにある。

## 受け取ったあと

指摘は結論ではなく仮説である。次の順に扱う。

1. **引用の実在を確かめる。** 示された`path:line`とコードが、その内容で実在するかを自分で突き合わせる。実在しない引用に頼る指摘は、結論が正しく見えても採らない。
2. **直すのは次の2種類だけ。**
   - 再現できた指摘。失敗シナリオを自分で実行する、落ちるテストを書く、動作確認で不合格になった、のどれかで確かめたもの。
   - 外したときの損害が大きい指摘。セキュリティ、データの損失、戻せない操作に関わるもの。再現できなくても、成立する条件を実装まで辿って確かめたうえで扱う。権限の境界は`fail-closed`などのラベルで合格にせず、何と何を比べ、どこで強制しているかを辿る。
3. **それ以外は既定で直さない。** 命名、将来の拡張への備え、文言の好み、再現できず損害も小さい指摘が当たる。1件ずつの採否の記録は要らない。
4. **未検証の懸念**は、損害が大きい種類のものだけ自分で確かめる。
5. **検査しなかった範囲**を読む。重要な範囲が残っていれば、自分で確かめるか、範囲を絞って追加で依頼する。返答に無いことを、問題が無いことの根拠にしない。
6. **修正したら、元の確認を再実行する。** 修正と再レビューの往復は既定で1回までとする。続けるときは、理由と打ち切る条件を記録する。
7. 最後に`git status`を確かめる（写しで起動したときは写しの側。動作確認では、本体のツリーに第三者の実行による変更が無いことも確かめる。待ち時間に自分や並行作業が加えた変更は除いて比べる）。

## 結果の報告

人へ返すときは、要約（3点以内）、直した指摘、直さないと決めた損害の大きい指摘とその理由、検査しなかった範囲、採用か再レビューかの推奨を書く。判断を任されたセッションは自分で判断し、毎回人間へ聞き直さない。同じ本文が再掲されても二重に報告しない。出力の取り出し方はproviderごとの参照ファイルにある。
