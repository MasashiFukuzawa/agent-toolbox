# 範囲を決めたテストの棚卸し

既存テストの棚卸し・統合・削除は、ユーザーが範囲を明示した場合にだけ行う。通常の機能追加やレビューの依頼から、サブシステム全体の棚卸しを推測しない。承認済みのタスク指示に範囲が書かれていれば、それを承認として扱い、取り直さない。任意の道具が無いことは限界として報告し、実行できる確認まで止めない。

## 手順

1. 基準の revision、対象のテスト、本番側の持ち主と呼び出し元、守られている契約を特定する。関連する確認を基準の状態で実行し、失敗や実行できなかったことを記録する。
2. 候補の assert と、重なっている他の証拠を読む。残す・直す・統合する・消すは、そのテストが実際に検出できる失敗で決める。テスト名や件数では決めない。同じ契約を守るケースはまとめて判断してよく、宣言ごとの台帳は要らない。
3. 消す前に、その契約を引き続き守るテストと、保つべき assert を特定する。判断がつかない候補は、足りない証拠を書いて残す。冗長な証明を消す前に、意味のある保護を残す側へ移す。消したテストだけが使っていた helper・export・fixture は、同じ変更で片付ける。
4. 承認された範囲だけを編集し、影響する確認を実行する。検出力が分からない場合は、本体を意図的に壊して落ちるかを確かめてよい（すべての棚卸しで必須ではない）。行う場合は、元のバイト列を保存して復元し、復元を確認してから再実行する。意図的な欠陥を残さない。
5. 契約とカバレッジの対応、実際の結果、残る限界を、既存の報告の中で伝える。基準で落ちていたテストは、範囲外の修理を許可する理由にならない。

範囲内の判断に証拠が揃い、残した契約が守られていれば完了とする。保てたと言えないものは、限界として開示する。

## 判断の基準

- 名前、実行の遅さ、リファクタリングで壊れやすいことは、それだけでは削除の理由にならない。
- 設定・プロトコル・権限・永続化・マイグレーションと、実際の振る舞いの契約は保つ。
- 約束されたバイト列・キー・パスを確かめるソースの検査は意味を持ちうる。文章の一致は、エージェントの振る舞いを証明しない。
- 調べる兆候: 自分自身との比較、テスト対象のコードが生成した期待値、重複した fixture や契約、期待する振る舞いを実装してしまっているモック、無関係なガードで落ちている異常系。
- テストの件数や削除した行数を成果の指標にしない。
