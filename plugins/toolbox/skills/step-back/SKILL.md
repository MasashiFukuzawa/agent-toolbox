# Step Back — 判断を目的から立て直す

目の前の障害や作業に没頭すると、「今すぐ止血できる案」「既存の手順どおりの案」に流れ、本来の目的を後退させる推奨を出しやすい。このスキルは、呼ばれた時点の判断を一歩引いて見直し、目的と一次情報の証拠から選択肢を組み直す。今の結論を正当化するためではなく、判断を変え得る材料を集めるために使う。

## 使いどころ

**明示的に呼ばれたときだけ使う。** 自分で条件を判定して起動しない。両ホストとも自動起動は設定で止めてあり、Claude Code では `/toolbox:step-back`、Codex では `$step-back` で呼ぶ。手順はどちらでも同じ。

対象は、呼ばれた時点で直前に出していた判断である。推奨案、実行中の対処、判断依頼の下書きなどを指す。会話から特定できなければ、一文で確認する。

呼ばれやすいのは次のような場面である。手順はどの場面でも同じ。

- 目的のために入れた変更を、戻す・無効化する案を推している。
- 原因を裏付ける証拠がないまま、対処を進めている。
- 同じ方針での失敗が続いている。
- 「既存の手順どおり」「早く戻せる」が、推奨の主な理由になっている。

## 手順

手順1を済ませたら、手順4の第三者レビューを先に起動する。待つ間に手順2・3を進め、手順5で合流する。

### 1. 目的を分解する

直前の判断より上位にある目的を、手段と分けて書く。

| 項目 | 書くこと | 例 |
|---|---|---|
| 守るべき制約 | 後退させてはいけないもの | 長期の鍵を本番に置かない |
| 回復・達成すべき機能と期限 | 何がいつまでに動けばよいか | 日次の取り込みを翌朝までに再開する |
| 望ましい手段 | 今選んでいるやり方 | 鍵なしのフェデレーション認証 |

- **手段を目的と取り違えない。** 手段を変えても制約と機能を満たせるなら、目的の後退ではない。逆に、制約を破る案は、止血として正しくても「目的の後退」と明示する。
- **制約を勝手に強めない。** 要件・決定・規程で確かめられた制約と、自分の推測を分けて書く。「鍵への依存を減らす」を「長期鍵は絶対禁止」と読み替えない。未確認の制約は、判断を左右するなら人間に確かめる点として残す。
- **待つことの損失も書く。** 停止や保留を続けると、誰に何がいつまでに起きるか。損失によっては、切り戻しが最善の案になる。

### 2. 原因を証拠で確かめる

- **仮説ごとに3つ書く。** 支持する証拠、反証になる観測、確かめるための最小の検証である。確度は根拠と一緒に示す。
- **一次情報を read-only で取りに行く。** 要約や記憶に頼らず、設定値・変更前後の差分・ログ・エラーコード・公式の仕様を見る。最初は「変更前後で何が変わったか」から当たる。仕様の確認は `technical-research` を使う。
- **証拠を示せない仮説は「未確認」と書く。** 確度が高く見えても断定しない。
- **副作用のある検証はここでは実行しない。** 本番で実際にトークンを発行する、処理を再実行する、設定を変える、といった検証は、選択肢の1つとして手順3に回す。

### 3. 選択肢を組み直す

- **最低限、2つを並べる。** 目的を保つ案と、止血案である。必要なら段階案（止血しながら根本解決へ進む案）を足す。型を埋めるために、同じ案を言い換えて並べない。
- **各案について4点を書く。**
  - 目的との整合：制約を守るか。機能をいつ回復するか。
  - 戻しやすさ：「設定を戻せるか」と「その間に起きた副作用（アクセス、データ、外部への送信）を戻せるか」を分けて書く。
  - 影響と待ち：停止の損失、人や外部の待ち。
  - 根拠：推奨を支える証拠と、推奨を覆す観測。
- **後戻りコストは `ai-native-engineering` の判断軸で評価する。**
- **推奨は言い切る。** 推奨案には、失敗したときの停止条件と戻し方を付ける。
- **暫定案を推すなら、根本解決とその時期を添える。** 原因が未確定で時期を言えないなら、代わりに「次の検証」と「再判断する時点」を約束する。

### 4. 逆providerの第三者視点を入れる

このスキルが呼ばれたことを、read-only レビュー1回の委任として扱い、確認なしで起動する。ユーザーが「レビューなしで」と言ったときは省く。

- **provider は自分と逆にする。** `second-opinion` を使い、Anthropic の Claude で動いているなら Codex を、OpenAI の Codex で動いているなら Claude を起動する。
  - 起動・待機・回収・受け取ったあとの検証は、そのスキルの手順に従う。
  - モデルと effort は、判断そのものが対象のレビューとして `model-selection` で選ぶ。
  - ユーザーが provider やモデルを指定したら、それに従う。
- **逆の provider が使えないときは、同じ provider へ黙って切り替えない。** CLI が未導入、認証切れ、起動に失敗した、などの場合である。原因を書き、第三者の視点なしで出したことを結果に明記する。
- **渡すもの：**
  - 手順1の目的の分解。
  - 一次情報の場所（ファイル、設定、ログ）。
  - 検討中の案。いま推している案（直前の判断を変えたなら、変えた後の案）を「反証の対象」と明示して渡す。
  - 要約だけを渡すと、同じ思い込みを共有してしまう。一次情報を直接見させる。
- **求めるもの：** 原因についての独立した見立て、目的を保つ別の案、推奨への反証、意見が割れたときに決着をつける観測。
- **1回の呼び出しでレビューは1回。** 返ってきた指摘は仮説として扱い、実物と照合してから採否を決める。

### 5. 判断を出し直す

既定の出力は次の5項目に絞る。手順1〜3の表や仮説の一覧は作業用であり、回答に再掲しない。案どうしの比較が判断の決め手になるときだけ、短い選択肢表を添える。

```markdown
結論: <推奨する案>。<目的（制約・機能と期限）にどう効くか、を1〜2文で>
決め手: <推奨を支える証拠と、待つ損失や戻しやすさの比較>。<原因は確度付きで、未確認なら未確認と書く>
次の検証: <推奨を確かめる、または覆す最小の観測>
再判断の条件: <停止条件と戻し方>。<暫定案なら、根本解決と時期（または再判断する時点）>
第三者の見解: <一致した点> / <相違点と、決着させる観測> / <実施しなかった場合はその理由>
```

第三者レビューへの依頼文は回答に再掲せず、送ったことと結果の採否だけを書く。

- **第三者と意見が割れたら、両論を並べる。** そのうえで、自分の推奨とその理由、何を観測すれば決着するかを示す。どちらを採るかは委任の範囲に従い、人間が判断する事項なら人間に返す。
- **実行はこのスキルの範囲外である。** 推奨案を適用するときは、通常の権限と確認の規律に従う。

## しないこと

- **承認済みの緊急復旧を止めない。** smoke 失敗時の自動 rollback などが該当する。実行してよいかを聞き直さず、権限があればそのまま実行に移る。比較や第三者レビューは復旧の後に回し、そのあとの「戻し直す」判断にこのスキルを使う。
- **原因が分かったふりをしない。** 確度の言葉で、証拠の欠けを埋めない。「Xの後も続くなら原因はXではない」のように、残った状態や副作用を見落とした排除もしない。
- **儀式にしない。** 判断が変わらない欄を埋めるために、調査やレビューを増やさない。
