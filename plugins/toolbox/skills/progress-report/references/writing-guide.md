# progress-report 執筆ガイド（詳細）

本文（SKILL.md）の各ルールの詳細・例・矛盾処理。書きながら迷ったらここを読む。

## 情報源チェックリスト（Mode B では上から順に確認）

特定のツール名には依存しない。実行環境にあるコマンド・ファイル閲覧手段で確認する。

1. **上位計画・タスク体系**: 計画ファイル（`~/.claude/plans/`、`docs/plan*`、`PLAN.md`）、エピック/親Issue、マイルストーン定義、ロードマップ。**本作業が属する「大元のゴール」を最初に特定する**
2. **バージョン管理の履歴**: コミットログ（`git log --oneline --stat -30` 等）、ベースブランチとの差分、未コミット変更、stash
3. **タスク管理**: TODO ファイル、チェックリスト、Issue / PR とそのコメント
4. **実行結果**: テスト・ビルド・lint の状態（実行可能なら実際に走らせる）、CI の状態
5. **作業ログ**: セッションログ、エージェントの作業メモ・レポートファイル

### どこまで掘るか

3つの問い＋目的、すなわち (1) **大元のゴールは何で、本作業はその何番目のピースか** (2) この作業は何を達成しようとしているか (3) どこまで終わって何が残っているか (4) 順調か、壊れて/詰まっているか — に答えられたら止めてよい。

「うまくいっていない兆候」（失敗テスト・revert・大量 fixup・中途半端な未コミット）を見つけたら浅く流さず、「なぜ今壊れたのか」（どの変更の波及か）まで遡る。読み手が最も知りたいのは順調な部分ではなく問題と判断が必要な箇所。

## 事実と推測の区別（Mode B では必須）

推測を断定口調で書いた報告は、間違った判断を誘発するため報告しないより有害。

- 痕跡から直接確認できたことは事実として書く（「テスト 3 件が失敗している」）
- 推測は推測と明示し根拠を添える（「認証方式の変更が原因と**推測される**（根拠: 失敗テストは全て auth モジュール、直前コミットで token 検証を変更）」）
- 確認できなかったことは「不明」と正直に書く。セクションを埋めるための創作をしない
- **痕跡同士が矛盾する場合**は、より新しく・実行可能な痕跡（テスト・コード）を意図の根拠として優先し、「計画書と実装が食い違っており、〜を正とみなした」と矛盾の事実と採った解釈を一行残す（読み手が解釈を覆せるように）。痕跡が挙動を部分的にしか定義していない場合も、定義済み部分は事実、未定義部分は「推奨つきの確認事項」として読み手に回す

## 用語 — 読み手の語彙で書く（ガードレール4の詳細）

閾値は「**バックエンド出身の一般的な EM の語彙**」。html-artifact の原則8（読み手の語彙を閾値にした3段階の判定順）と同じ構造で、機構だけ Markdown 向けに翻案している。判定順はこの順で止まったところが答え:

1. **言い換えられるか → 言い換える（第一選択）**。組織・プロジェクト固有の略語、セッション内で生まれた呼称、内部システム名の略記、chat 上の口語的な短縮形は一般名詞に言い換える。「補足を付ければ使ってよい」ではない
   - 例: 「親controller」→「メインセッション」、「done full」→「リポジトリの完了品質ゲート」、「sealed artifact」→「ビルド成果物」
2. **閾値内か → 素のまま使う**。API・CI/CD・rollback・staging・PR・schema・race condition 等、バックエンド出身の EM が説明なしで理解できる業界標準の用語は補足しない（補足だらけの文はそれ自体がノイズ）
3. **閾値を超え、言い換え不能か → 初出で一言補足**。「PASETO（JWT の代替トークン形式）」程度の括弧内1フレーズ。2回目以降は素のまま使う

- 迷ったら: 言い換えを先に試す。言い換え不能で閾値の判断もつかない語だけ、補足する側に倒す
- 1文に補足が2つ以上並ぶなら、その文自体を書き直す（原因は語彙ではなく詰め込み）

## 全体マップの書き方

- **大地図**はマイルストーン単位。大元ゴールの全行程が1画面の表で見渡せる粒度にする
- **小地図**は現在地マイルストーンの内訳だけを展開する。粒度の目安は「**PR またはレビュー可能な作業のまとまり**」で、**3〜7行**に収まるように選ぶ。行が多すぎるなら粒度を上げてまとめ、内訳が1〜2項目しかない（始めたばかり・単一ステップ）なら小地図を省略して「次の一手」だけ書く
- **現在地（🔄）の件数による分岐**: 0件（全完了または全停止）なら小地図を省略し、「全マイルストーン完了」または「作業停止中（理由）」を1行で書く。複数件（並列作業）なら本報告の主対象1件を小地図にし、残りの 🔄 は大地図の行に現在の状態を一言添える
- **上位計画が特定できない場合**: マイルストーン総数を創作しない。X/Y・進捗バー・大地図を省略し、ステータス行に「全体母数は不明（上位計画は痕跡から特定できず）」と書いた上で、確認できた作業単位の一覧と状態を §3 に載せる
- 進捗バーの検算: 1マイルストーン=1セルで、セル数=大地図の行数、✅=`█`、🔄=`▓`、⬜=`░`（例: 5件中2完了・1作業中なら `██▓░░`）。バーと表が食い違う報告は数字への信頼を全部壊す

## 健全性（§4）の書き方

読み手がこの節で判断したいのは「介入・再計画が必要か」。事実の列挙ではなく**自己申告の判断**を書く。

- **ペース**: 当初想定（計画ファイル・見積もり・過去の報告）と比べる。比較対象がなければ「初回報告のため基準なし」と書く
- **寄り道・過剰設計の判定目安**: ①当初計画にないタスクに着手している ②同じ問題への試行が3回以上繰り返されている ③要求されていない汎用化・抽象化・機能追加をしている — に該当したら正直に申告し、「続ける／巻き戻す／判断を仰ぐ」のどれかを添える
- **再計画**: 提案する場合は内容を1行で。詳細な新計画はこの報告に書かず、承認されてから別途作る
- 取り繕わない。「順調です」と書いてよいのは3項目すべてに根拠を持って No と言える時だけ

## 執筆ルール詳細

- **同一事項が複数セクションに該当する場合**（例: スコープ外だが人間対応が必要なリスク）: 各セクションにはそのセクションの役割の側面だけを書く — §2 は「何をしてほしいか」、§3 は「進行の事実」、§4 は「健全性の判断」。詳細は最も役割が合う1箇所に置き、他からは一行+参照で繋ぐ
- **数字の検算**: 内訳の合計が総数と一致するか検算する（成功+失敗+skip=総数。skip を成功に数えない）。テストランナーの failure/error/skip の区分は丸めない
- **メタ情報を混ぜない**: 保存先パス・使用ツール・前任者のローカルパス等、読み手の判断に関係しない舞台裏は報告の外（呼び出し元への返答側）へ
- **急ぎ度の書き方**: 高/中/低のラベル単独にせず「それが解消されないと何がいつから止まるか」を必ず添える
- **ステータス色**: 🔴=ブロッカーまたは読み手の判断待ちあり、🟡=リスクはあるが進める、🟢=どちらもない。迷ったら悪い方の色

## Good / Bad 例

同じ状況（決済モジュールのリファクタリング中、テスト2件失敗、レート制限の仕様判断が必要）の対比。

**Bad** — 活動報告になっている・問題が最後尾・網羅列挙・上位文脈なし:

```markdown
# 進捗報告
## やったこと
- payment.ts を修正
- payment_test.ts を修正
- utils.ts の import を整理
-（…以下12項目続く）
## その他
特に問題ありません。順調です。
```

→ 大元の何のどこをやっているか分からない。何が重要か分からない。失敗テストに触れず「順調」は事実に反する。依頼が存在しない。読み手はこの列挙から何も判断できない。

**Good** — 3つの問いに正面から答える・依頼明示・健全性を自己申告:

```markdown
# 進捗報告: 決済リトライ機構の実装（2026-06-06）

**ステータス**: 🔴 — マイルストーン 1/3 完了 `█▓░` ＋ 2つ目「リトライ機構」が仕様判断待ち

## 1. TL;DR
- 大元は「決済安定化イニシアチブ」（全3タスク）。本作業はその2つ目「リトライ機構」
- 実装完了・テスト 42 件中 40 件成功。残り2件はレート制限時（HTTP 429）の挙動が仕様未定義で失敗中
- **判断のお願いが1件**（→ §2）

## 2. 要対応・要判断
1. **HTTP 429 でリトライすべきか即時エラーにすべきか決めてください。**
   外部 API の課金体系（リトライが課金対象か）に依存するため実装側では判断できません。
   決まればテスト2件を確定でき本件完了。返答があるまで次タスク（3つ目: 監視強化）へ先行着手します。

## 3. 全体マップ（大地図 → 小地図）
決済安定化イニシアチブ: 決済失敗率を下げる全3タスクの改善計画。

**大地図** — マイルストーン一覧:
| # | マイルストーン | 状態 | 検証レベル |
|---|---|---|---|
| 1 | タイムアウト調整 | ✅ 完了 | 本番反映済み |
| 2 | **リトライ機構（本作業）** | 🔄 仕様判断待ち | ローカルテストまで |
| 3 | 決済監視の強化 | ⬜ 未着手 | — |

**小地図** — 現在地「リトライ機構」の内訳:
| # | タスク | 状態 |
|---|---|---|
| 1 | リトライ本体の実装 | ✅ 完了 |
| 2 | 単体・結合テスト | 🔄 40/42（2件は §2 の判断待ち） |
| 3 | **PR 作成・レビュー** | ⬜ 未着手 |

**次の一手**: §2 の返答待ちの間、マイルストーン3の設計調査に先行着手する

## 4. 健全性（計画対比）
- **ペース**: 想定通り（計画では今週中にマイルストーン2完了予定、判断が今日つけば間に合う）
- **スコープ**: 膨張なし。リトライの汎用化（他 API への適用）は要求されていないため実装していない
- **再計画**: 不要
```
