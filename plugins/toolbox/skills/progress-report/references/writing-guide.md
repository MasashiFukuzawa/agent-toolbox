# 報告の根拠と判断支援

## 情報収集の範囲

最初にユーザーが指定した目的・計画・親Issueを確認し、関連するタスクの状態と成果の証拠を照合する。ソースが未指定なら現在repoの計画・tracker・履歴から探す。他repoやホーム全体を無差別に探索しない。

優先する証拠は主張によって異なる。意図/受入条件は承認済み計画やIssue、実装はdiff/commit/CI、運用状態は配備結果・実機証跡。食い違いは片方を消さず「計画はA、実装はB、判断が必要」と表す。

目的・現在地・残る条件・次の判断を説明できたら探索を止める。報告のために全面監査や復旧実装へ発展させない。失敗の原因が未確定なら観測事実と仮説を区別し、必要な調査を次の行動にする。

## 数字と期限

- 件数には母数と完了の意味を付ける。テスト数をプロダクト進捗率へ換算しない。
- 大小の違うタスクの単純平均で公開準備率を作らない。必須ゲートが未達なら件数が多く完了していても明示する。
- 日程は依存と並列可能性、レビュー/統合、外部待ち、受入の期間から考える。根拠のない精密な完了時刻を出さない。
- 余裕は「期限までの時間」ではなく、残工程を差し引いた幅として扱う。未見積もりや不確実性の大きい工程があれば余裕も未確定とする。
- 「前回比」は前回の報告/時点を特定する。基準がなければ差分を創作せず、今回確認できた状態を短く返す。

## 人間が判断できる書き方

悪い例: 「#123がblocked。A/Bどちらにしますか？」

良い例: 「公開前のデータ移行が権限不足で停止しています。今日中に承認されれば明日検証へ進めます。推奨は必要な移行権限だけを期限付きで付与する案です。承認しない場合は公開日を再計画します。」

短くても、目的・選択肢の差・推奨・何が止まるかが分かるようにする。AI側で解消できる調査不足を人間の選択にすり替えない。

全体報告の例: 目的/公開条件を一行、主要作業と成立していない条件の表、期限見通し、必要な判断、次の行動。これは例であり必須テンプレートではない。

局所報告の例: 「検索機能は実装・CIまで完了。いまは実機受入待ちです。全体公開には別の移行も必要です。次はテストアカウントで受入を確認します。」

## ステータスと語彙

色を使うなら意味をラベルでも示す。赤は目標未達が確定/進行不能など、黄はリスクがあるが進行可能、緑は確認範囲の必要条件が成立している状態として使える。不明は不明と示し、色へ丸めない。局所と全体の状態を分ける。

Issue番号は補助参照で、主語は能力や作業の内容。内部略語は言い換え、必要な専門語だけ初出で短く説明する。読み手を常にエンジニアと仮定しない。

何をしたかより何が利用可能になったかを書く。ただし未配備を利用可能と表現しない。ログ・コード全文は載せず、判断に効く根拠へのリンクを残す。
