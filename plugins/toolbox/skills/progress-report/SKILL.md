# Progress Report — 現在地と次の判断

活動ログではなく、読み手が「何を目指し、今どこで、何が完了を左右し、自分は何をすべきか」を判断できる報告を作る。文章は必要最小限。背景・因果・選択肢・重大リスクまで削らない。固定の章立てを埋めることを目的にしない。

## 入力: progress-report [--ascii] [--html] {自由文の上書き指示}

フラグは要求しない。スキル名に続く自由文と同じ依頼内の指示から、焦点・粒度・読み手・比較時点・形式を解釈する。指定された部分だけ既定を上書きする。

`--ascii` と `--html` は任意の出力形式指定。シェルコマンドではなくスキルへの入力として解釈し、自由文の前後どちらでも受け付ける。焦点の指定に `--scope` などの構文は要求しない。「HTMLで」「ASCII図で」も同じ意味で扱う。

| 依頼 | 解釈 |
|---|---|
| progress-report | 大元の目標に対する全体状況 |
| progress-report 今やってることに絞って | 現在作業を主対象にし、全体への重大な影響だけ添える |
| progress-report 公開日に間に合うかを中心に | 残工程・依存・外部待ち・余裕・不確実性を優先 |
| progress-report 前回から変わったことだけ | 比較基準を特定し、変化と判断への影響だけ示す |
| progress-report 技術詳細なしで、私が判断すべきことを | 読み手の判断に必要な背景・選択肢・推奨・期限を示す |
| progress-report HTMLで、図解多めに | 内容は本スキル、表現はhtml-artifactで作る |
| progress-report --ascii 今どこが詰まっているか | 会話内の図解で依存・待ちを示す |
| progress-report --html 公開までの見通しを中心に | 図表付きHTMLを生成・保存する |
| progress-report --ascii --html | 同じ根拠から会話内の図解要約とHTMLを両方作る |

合理的に解釈できれば確認で止めない。異なる解釈で判断が変わる場合だけ確認する。過去の一時的な上書きを次の依頼へ無断で持ち越さない。自由文は事実・証跡・権限・安全境界を上書きしない。

## 表示スキルへの連携

先に本スキルで対象・基準時点・根拠・現在地・残条件・次の判断を整理し、指定された表示スキルを読んで表現する。固定の中間ファイルや報告テンプレートは作らない。

- **指定なし**: チャット報告。必要なら表や小図を使うが、保存ファイルは作らない。
- **--ascii**: `ascii-diagram` を読み、会話内の図解を重視する。タイムライン・工程帯・ツリー・依存図などから選ぶ。短い結論・比較表・根拠リンクを併用してよく、すべてを箱と線やコードブロックへ変換しない。大きい図は小図へ分割し、保存形式へ勝手に切り替えない。
- **--html**: `html-artifact` を読み、図表付きの自己完結HTMLを保存する。この指定をファイル生成の明示依頼として扱う。保存・アクセシビリティ・表示検証は同スキルに従い、チャットには結論と成果物リンクを返す。公開・アップロードは含まない。
- **両方**: 同じ基準時点・根拠から、ASCII要約とHTMLを作る。詳しさは異なってよいが、状態・数値・結論・重大リスクを食い違わせない。HTMLへASCII図をそのまま貼る義務はなく、媒体に適した図を選ぶ。

連携先は表示品質を担当し、報告範囲や事実の正本を変更しない。必要な問いは維持するが、見出し・順番・図種は自由に選ぶ。表示スキルが利用できなければ連携済みと装わず不足を伝え、作成可能なチャット報告を返す。

## 既定は俯瞰から

1. **大元の目的と完了条件**を、指定された計画・親Issue・マイルストーンから確認する。直近の作業や自分の担当だけを全体とみなさない。
2. 主要な作業群の完了・進行中・未着手・停止中を確認し、現在作業がどこに当たるかを示す。複数レーンなら期限を左右するレーンを落とさない。
3. **目標到達を左右する条件**を特定する。残作業、依存、外部待ち、受入・配備、リスク、余裕を見る。件数の完了率だけで順調と判定しない。
4. **次の行動と人間の判断**へつなぐ。誰が何をいつまでに行い、何が変わるかを示す。判断不要ならその旨と次に進めることを短く書く。

局所指定時は全体表を押し付けないが、「この作業は完了、全体は移行待ち」のように重大な外部依存を短く残す。指定範囲から全体の健全性を断定しない。

## 情報の確かさ

自セッションの記憶を証拠へ結び付ける。再構築・情報の矛盾・見積もりがある場合は [執筆ガイド](references/writing-guide.md) を読む。

- 計画は目標/順序、Issueは受入条件/判断、PR/CIは実装、配備記録は実環境の証拠。新しいコードを根拠に承認済みの意図を勝手に変更しない。
- 全体を確認できなければ確認範囲と未確認範囲を明示する。母数、進捗率、日程、余裕を創作しない。
- 事実、推定、未確認を区別する。古い証拠は確認時点を添える。未検証・skip・配備待ちを完了に数えない。
- 報告のためにIssue状態更新・Job実行・配備などの副作用を起こさない。原因未確定は未確定として、判断に必要な範囲のread-only確認に留める。

## 構成と図表

冒頭に目的と現在地、最も重要な判断または見通しを置く。その後は問いに適した構成を選ぶ。TL;DRとステータスと表で同じ説明を繰り返さない。

図表は積極的に使い、読み手の比較・位置づけ・依存理解を助ける。形式のノルマは作らない。

| 伝えたいこと | 向く表現 |
|---|---|
| 全体の現在地 | 主要作業の状態表、工程帯 |
| 期限・並列・外部待ち | タイムライン、担当別レーン |
| 判断と代替案 | 効果・リスク・期限を揃えた比較表 |
| 残作業の量・余裕 | 根拠ある棒グラフ、幅を持つ期間表示 |
| 少数の依存 | 短い関係図、依存列付きの表 |

箱と線の図を万能に使わない。重要な関係が短文や短い一覧で明快なら無理に図にしない。チャットではMarkdownの表や小図、保存する可視化が求められればhtml-artifactへ渡す。HTML化のためだけに報告を膨らませない。

判断依頼は「何を決めるか・なぜ今か・選択肢・推奨と理由・決めない場合の影響/期限」を揃える。Issue番号や内部略語を見出しの主語にせず、初見で分かる内容名にする。技術語の説明水準は読み手に合わせる。

重要な根拠へ少数のリンクを添える。詳細は必要時に辿れるようにするが、推奨を覆し得る情報を「詳しくは聞いて」と隠さない。全タスク一覧を求められたら、短さのために勝手に対象を削らず概要と全量を分ける。

## 出す前の確認

- 初見の人が目的・現在地・残る主要条件・次の行動を答えられるか。
- 全体報告で直近タスクだけを説明していないか。局所指定で不要な全体説明を押し付けていないか。
- 「順調/遅延」の根拠があるか。人間対応があるだけで全体を赤にしていないか。
- 数字・日付・検証段階・証拠の時点が一致しているか。
- 文章や図表を減らしても理解が変わらない重複はないか。

既定は日本語のチャット報告。ファイル保存は明示依頼時のみ。ファイル生成が依頼された場合も、チャットには結論とリンクを短く返す。
