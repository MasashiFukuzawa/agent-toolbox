# モデル選択

最安モデルでも最強モデルでもなく、必要な品質を満たし、時間・費用・修正往復・controllerの確認負荷を含めた総コストが妥当なモデルを選ぶ。出荷品質の判断責任はcontrollerに残る。

## 正本と権限

- モデルID・effortの初期候補は [モデル表](references/models.md) が唯一の定義元。呼出し側へ表を複製しない。起動例は選択済みのmodel/effortを受け取る。
- ユーザーの明示モデルfamily・effort・禁止・予算と、実行ホストの許可範囲を優先する。版の解決はモデル表の既存方針に従い、置換を通知する。利用できない系列を黙って別系列へ置換しない。
- モデル選択が委任されたcontrollerは、許可範囲内でprovider・モデル・effortを決定できる。単に「自律で」と言われただけで、未許可providerへの情報送信や利用制限の解除を推定しない。
- 最上位モデルは明示指定、またはそのモデルを含む選択権限の事前委任がある場合に利用できる。既に委任されていれば毎回人間へ聞かない。
- 単発のprovider未指定レビューで選択権限も不明なら確認する。provider指定だけなら、そのprovider内の既定候補から選ぶ。

## 判断

1. 役割（実装・調査・独立レビュー）、受入条件、不確実性、失敗時の影響、期限、利用可能モデルを確認する。
2. 難所が設計で解決済みかを見て初期候補を選ぶ。認証などの題材や差分量だけで昇格しない。一方、難所が明白なら軽量モデルでの失敗を経由せず適切なモデルを選んでよい。
3. モデル・effort・選択理由を一行で作業記録へ残す。未測定の精度差や費用対効果を数値で捏造しない。
4. 結果の根拠、未検査範囲、修正往復、経過時間を見て再評価する。成果物を読まず「強いモデルだから正しい」と採用しない。

深さ不足なら、まず対象と質問を明確にし、必要ならモデルを上げる。effortだけを際限なく増やさない。同じ失敗の反復はモデルだけでなく、仕様・入力・ツール不足も診断する。

## 役割ごとの境界

- 実装workerは局所判断と検証を行い、controllerへ提出する。最終受入はしない。
- 独立reviewerはread-only。懐疑的検証と根拠を返し、実装・投稿・再帰レビューをしない。起動方法と権限は各review skillを必ず読む。
- controller自身が選択された役割をこなせない場合、能力の高いworkerやadvisorへ調査を委任できるが、品質責任を転嫁しない。
- 独立再レビューは新規文脈、同じ処理の回収・追加質問は正確なsession IDで継続する。モデル変更と独立性の確保を混同しない。

モデル表は運用上の初期値であり、普遍的な性能順位ではない。実測や公式の対応情報と矛盾した場合は根拠を記録して更新を提案する。タスクごとの一時的な選択は共通表へ自動で書き戻さない。
