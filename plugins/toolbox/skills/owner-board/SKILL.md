# Owner Board — オーナー連絡板

オーナーが連絡板を開いた最初の画面で「作業がいまどこにいて、自分が何をいつまでにすればよいか」が分かり、各依頼を聞き返さずに答えられる状態を保つ。
連絡板はHTMLを直接書いて更新する。JSONや生成スクリプトは使わない。チャットに流れやすい手順・入力値・背景を連絡板へ集める。
連絡板の作成は、外部公開・他者への送信・実行権限の拡張を許可しない。

## 役割分担

| スキル | 担当 |
|---|---|
| owner-board | 人間への依頼の要否、画面の構成、依頼カードの書き方、Q番号、回答の記録、中継 |
| html-artifact | 見た目（DESIGN.md）、図の描き方、保存先、開き方。HTMLを書く前に「図で語る」「実装の落とし穴」「保存先」とDESIGN.mdを読む。結論ブロックとAsIs/ToBe図は連絡板では使わず、本スキルの構成に従う |
| progress-report | 目的・マイルストーン・現在地の材料。連絡板の「いまの状況」は同じ材料から書き、タスク台帳を複製しない |
| autopilot | 実行・委任・権限・優先順位、判断待ちの扱い。回答が許可する対象・操作・環境・条件を確認する |

単一セッションでも使える。複数セッションやautopilotを起動するためのスキルではない。
連携先が利用できない場合は、利用したと装わず、必要な基準を本スキルの範囲で満たす。

## 依頼を載せる前に

- 人間が決める必要があるか、AIが既存の権限と根拠で解決できるかを判断する。省いても困らない確認は出さない。既に受けた承認を取り直さない。
- 判断と作業を分ける。判断は推奨を1つに決め、理由と欠点を添える。未検証・推定はその旨を書く。
- 報告だけなら「いまの状況」か別資料へのリンクにし、回答不要の報告にQ番号を割り当てない。
- 急ぎを勝手に作らない。期限は日付・時刻・タイムゾーンで書き、今日が期限なら「今日」とも書く。
- 準備中の論点は、まだ答えなくてよいこと、何が揃ったら提示するかを書く。

## 保存先とファイル

保存先はhtml-artifactの「保存先」に従い、`<project>/YYYY-MM-DD_owner-board_<slug>/` を作る（日付は板を作った日）。
同じ作業の連絡板は同じdirectoryを使い続ける。作る前に既存の板を探し、別の作業の板を上書きしない。

| ファイル | 中身 |
|---|---|
| `owner-board.html` | 本体。名前を固定し、通知のリンク先を変えない |
| `owner-board-archive.html` | 回答済み・取り下げの記録 |
| `owner-board-<session-id>.html` | 担当板が必要な場合の本体。記録は `owner-board-<session-id>-archive.html` |
| 内容名の `.html`、`diagrams/` | 込み入った解説資料と図。関連するQ番号と連絡板へ戻るリンクを付ける |

出発点は `assets/example/` の2ファイル。コピーし、架空の内容をすべて実際の内容に置き換える。CSSはそのまま使う。
公開repoへ実運用の板を混ぜない。サンプルは実案件の匿名化ではなく、独立した架空の内容で書く。
場所・更新担当・統合役を最初に共有する。書込みに失敗したら保存できたと装わない。

## 画面の構成

上から次の順に置く。答え方の説明、凡例、見出し上の小さなラベル（eyebrow）、前置きの文は置かない。

1. **タイトルと更新情報**: タイトルは作業名（例「検索機能リニューアルの連絡板」）。下に1行で、内容を更新した時刻（タイムゾーン付き）と更新担当。表示を直しただけでは時刻を変えない。
2. **いまの状況**: 次をこの順に置く。
   - 目的を1行。何が満たされれば終わりかを書く。
   - マイルストーンの帯。完了・いまここ・未着手を文字でも示し、日付を添える。
   - 「やっていること」「止まっていること」「見通し」を1行ずつ。止まっていることには原因のQへのリンクを付ける。
   - 目的とマイルストーンは計画・親Issueなどの正本から取り、創作しない。確かめられない項目は「未確認」と書く。
3. **あなたへのお願い N件（今日まで M件）**: 番号・期限・一行の問い・推奨（作業なら手順数と所要時間）だけの表を置く。0件なら「いまお願いはありません」と書き、空の表は出さない。準備中は件数に含めない。
   表の下に、回答を受け取ったが反映や中継が終わっていないQを1件1行で書き、追加の回答が要るかを明記する。
4. **依頼カード**: 期限の早い順に並べる（次節）。
5. **準備中**: `<details>` に折りたたむ。summaryに番号と内容、回答不要であることを書く。
6. **末尾**: 記録ページと、計画などの正本へのリンク。

1280×800の最初の画面に、タイトル・いまの状況・お願いの表が収まるようにする。各要素の高さを足して見積もり、収まらなければ状況の各行を削る。

## 依頼カード

見出しの上にQ番号・種類（判断／作業）・期限を並べ、見出しは問いを一行で書く。本文は「背景・課題・目的・相談事項」の4行を左のラベル列とともに並べ、相談事項の行だけAccent Tintで強調する。

| 行 | 読み手の問い | 書くこと |
|---|---|---|
| 背景 | そもそも何の話か | 対象と、読み手が知らない前提・用語。初見で「これ何？」と聞かれそうな語はここで説明する。経緯は書かない |
| 課題 | 答えないと何が困るか | 何が止まり、誰に何がどれだけ起きるか。数字・期日で書く |
| 目的 | 何が満たされればよいか | この判断・作業で到達したい状態 |
| 相談事項 | 自分は何をすればよいか | 判断と作業で中身が変わる（下の表） |

| 種類 | 相談事項に置くもの |
|---|---|
| 判断 | 選択肢表（推奨の行を強調し、内容・良い点・欠点の列）、決め手、決めない場合の影響、返信例。回答で次の動きが変わるなら「回答後に起きること」 |
| 作業 | 番号付きの手順と入力値・コマンド、所要時間、返してほしいこと、やらない場合の影響、返信例 |

- 各行は1〜3文。同じ事実を背景と課題で言い換えて二度書かない。
- 決め手は、推奨案だけが持ち他案に無い理由を1つにする。
- Issue番号・内部略語・作業中に付けた呼び名だけで語らない。
- 欠点・期限・推奨を覆す条件・作業の手順は折りたたまない。
- 判断材料の図や表は、選択に効くものだけを `<details>` に入れる。summaryは「2つの案の日程を比べる」のように中身が分かるラベルにする。選択と無関係な運用図は載せない。
- 手順・入力値・コマンドをチャットへ転載しない。
- 作業に秘密の値が要るなら、オーナーの端末で非表示入力して登録する手順を書く。値をコマンド引数・履歴・HTML・チャットへ残させない。返信は「登録済み」などの結果だけにする。

| 行 | 聞き返される書き方 | 答えられる書き方 |
|---|---|---|
| 背景 | 試用の範囲が未決 | 公開前に社員が実際の業務で使い、検索結果のずれを見つける「社内試用」に入る |
| 課題 | 早めに決めたい | 試用者が決まらないと案内を送れない。1日遅れるごとに公開日までの余裕（推定3営業日）が1日減る |
| 目的 | 試用をうまく進める | 11/20までに、公開してよいか判断できるだけの不具合を集め終える |

### 図と安全

- 図はhtml-artifactの「図で語る」に従い、inline SVGで描く。`role="img"` と要点を書いた `<title>` を付ける。
- script、イベント属性、`foreignObject`、外部の画像・CSS・フォントを使わない。リンクは `https:` と相対パスだけにする。
- Issue本文やログなど外から取り込んだ文字列は、`&` `<` `>` `"` をエスケープして埋め込む。

## 最新化

1. **追加**: 本体と記録ページの全Q番号を確認し、最大の番号より大きい番号を採る。統合板は `Q1`、担当板は `<session-id>-Q1`、小問は `Q5-1` のように親へ結び付ける。番号は再利用しない。選択肢は `1` / `2` とし、ラベルをセッション名と衝突させない。
   提示後に問い・対象操作・条件・選択肢の意味を変えるなら、旧Qを理由付きで取り下げて新しいQで出し、新Qの背景に旧Qとの関係を書く。誤字修正など意味を変えない直しは同じQでよい。準備中から提示する時点で意味を固定する。
2. **回答受領**: 番号と回答を照合する。「全部1」は指定された小問だけに適用する。判断が分かれる曖昧さだけ確認する。解説の要求や表示への感想を回答・承認として扱わない。
3. **記録化**: カードを本体から外し、記録ページの先頭へ移す。カードの4行は書き換えずに `<details>` へ入れ、回答の原文・受領時刻・その後の対応・中継先ごとの状態を書き足す。取り下げは理由を書く。記録ページの項目は消さない。提示済みQが参照する図や解説資料は上書きせず、変えるなら別名で保存する。
4. **反映**: 回答の受領と、それに基づく作業の反映を分ける。反映が終わるまでは、本体の「お願い」の表の下と記録ページの両方に反映中と書く。回答が許可する範囲を確かめてから作業し、終わったら「完了」と結果に書き換える。
5. **更新**: 内容の更新時刻を直し、「出す前の確認」を行って通知する。

開始時に、回答を受け付ける各セッションへ板の場所・更新担当・回答受領と中継の運用を共有する。Q番号だけの返信で本スキルが自動で起動するとは保証しない。共有できない場合は、更新担当へ直接回答するよう案内する。
一枚の板の更新担当は一つのセッションにする。他のセッションは板を直接編集せず、更新担当へ情報を渡す。同時更新のためのlock・自動マージは無い。

## 複数セッションと中継

[セッション間の運用](references/coordination.md) を複数セッションの開始時・担当交代時に読む。
判断・承認・権限・優先度・セッションをまたぐ事項は統合役の板へ集め、担当固有の論点を担当板に置くなら統合板からリンクする。同じ質問を両方で編集しない。
どのチャットで回答を受け取っても、依存する次の操作に進む前に統合役と関係担当へ中継する。送信の成功を確かめてから記録ページに「共有済み」と書き、それまでは本体と記録ページに中継待ちとして残す。
利用可能で許可されたセッション間通信だけを使い、無断でメール・Chat等の外部送信を追加しない。

## 通知と開き方

チャットにはQ番号と一言、連絡板のリンクだけを書く。

```text
Q12：試用の始め方の判断をお願いします。［連絡板のQ12へのリンク］
Q13：サンプルデータ確認の手順を載せました。［連絡板のQ13へのリンク］
Q12：回答を記録し、関係担当へ共有しました。［連絡板へのリンク］
```

初回と重要な新規依頼の時だけ、保存した板をOSの標準の方法で開く。通常の更新は通知とリンクだけにする。これはhtml-artifactの「保存後すぐ開く」より優先する。ユーザーの別指定には従う。
ブラウザでの表示確認はhtml-artifactと同じく行わない（頼まれた場合はbrowser-operationsを読んでから行う）。

## 出す前の確認

保存後にコードを読み返し、次を確認・修正する。

1. 最初の画面に、タイトル・いまの状況・お願いの表が収まるか（要素の高さを足して見積もる）。
2. 各カードの4行が読み手の問いに答え、初見で意味の分からない語が残っていないか。推奨・欠点・期限が見えるか。
3. 表・カード・記録ページのQ番号と期限が一致しているか。番号を再利用したり、記録を消したりしていないか。
4. ページ内の `#Q番号` と、記録ページへのリンクがすべて存在するか。
5. 未反映の回答や中継待ちを、終わったように見せていないか。
6. scriptや外部参照が無く、取り込んだ文字列をエスケープしたか。
7. 秘密・個人情報・企業固有情報・内部URLを公開物やサンプルへ混ぜていないか。
