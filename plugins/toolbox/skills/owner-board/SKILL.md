# Owner Board — オーナー連絡板

オーナーが「何を、なぜ、いつまでに、どう答えればよいか」を一枚で把握できる連絡板を保つ。
JSONを正本、自己完結の静的HTMLを閲覧用とする。チャットに流れやすい手順・入力値・背景をHTMLへ集約する。
連絡板の作成は、外部公開、他者への送信、実行権限の拡張を許可しない。

## 役割分担

| スキル | 担当 |
|---|---|
| owner-board | 人間への依頼の必要性、固定番号、追加・回答反映・記録化、通知と中継 |
| html-artifact | 図表の表現、自己完結、アクセシビリティ、実表示の確認。初回制作・表示変更時に読む |
| progress-report | 目的に対する現在地と判断材料の整理。詳しい報告は別資料へリンクし、タスク台帳を複製しない |
| autopilot | 実行・委任・権限・優先順位、判断待ちの扱い。回答が許可する対象・操作・環境・条件を確認する |

単一セッションでも使える。複数セッションやautopilotを起動するためのスキルではない。
連携先が利用できない場合は、その機能を利用したと装わず、必要な基準を本スキルの範囲で満たす。

## 依頼を載せる前に

- 人間が決める必要があるか、AIが既存の権限と根拠で解決できるかを判断する。
- 目的、人間に聞く理由、省いた場合の影響を一行ずつ言えるようにする。省いても困らない確認は出さない。
- 判断と作業を分ける。判断は推奨を先頭に置き、理由と欠点を添える。未検証・推定はその旨を明記する。
- 報告だけなら冒頭の短い状況説明か別資料へのリンクにし、回答不要の報告にQ番号を割り当てない。
- 急ぎを勝手に作らない。「今日」「近日」などの文字と色を併用し、期限があれば日付・時刻・タイムゾーンも書く。
- 準備中はまだ答えなくてよいこと、何を準備し、何が揃ったら提示するかを明記する。

## 保存先・初期化

保存先はユーザー指定 → プロジェクトが明示する成果物規約 → repo外の永続state領域。
既定のstate領域は環境のstate root、無ければホーム下の `.local/state/agent-toolbox/reports/owner-board/` とする。
既存run IDなどの作業識別子でdirectoryを分け、無ければ内容を表すslugと開始時刻で識別する。
別の作業の連絡板を上書きせず、場所・更新担当・統合役を最初に共有する。私的な運用では成果物directoryを所有者のみアクセスできるpermissionにする。
書込先が利用できなければ理由を示して代替場所を確認し、保存・表示が成功したと装わない。

- 統合板: `owner-board.json` と `owner-board.html`。
- 担当板が必要な場合: `owner-board-<session-id>.json` と同名のHTML。
- 図: 同directory内の `diagrams/`。解説資料は内容を表すHTML名とし、連絡板へ戻るリンクを付ける。
- 公開repoへ実運用のJSON・HTML・図を混ぜない。サンプルは実案件の匿名化ではなく、独立した架空の内容で書く。

最初に [データとCLI](references/data-format.md) を読む。
`assets/example-board.json` を `owner-board.json` として保存し、`assets/diagrams/`、`assets/explanation.html` を成果物directoryへコピーして出発点にできる。
サンプルの依頼・期限・回答を実運用の事実として残さず、不要な項目は初回利用前に除く。
HTML雛形は `assets/board-template.html`。CSSは読み手に合わせて調整できるが、必須部分の情報構造を保つ。

```bash
python3 <skill-dir>/scripts/owner_board.py validate --data <artifact-dir>/owner-board.json
python3 <skill-dir>/scripts/owner_board.py render --data <artifact-dir>/owner-board.json --output <artifact-dir>/owner-board.html
```

`<skill-dir>` と `<artifact-dir>` は実際の場所に置き換え、空白を含むパスはshellに合わせて引用する。
スクリプトはJSONを変更せず、HTMLの生成時刻を表示する。回答の時刻はJSONに記録する。
検証に失敗した場合は既存HTMLを保持する。生成済みHTMLを直接編集したり、正規表現でカードを移動したりしない。

## HTMLの構成とカード

冒頭の目的・更新担当・更新時刻・答え方・凡例 → 開いている項目一覧 → 個別カード → 回答後の処理待ち → 折りたたんだ記録。
回答待ちゼロは明示し、空の表は出さない。準備中は回答待ちの件数に含めない。
重大な反映待ち・中継待ちは記録に隠さず、追加の回答が必要かをsummaryに明記する。
訂正の確認が必要な場合は新しいQへ関連付け、回答済みの元Qを保持する。

| 種類 | 必須の内容 |
|---|---|
| 判断 | 問い、目的、背景、あなたに聞く理由、選択肢と推奨・理由・欠点、決めない場合の影響、返信例 |
| 作業 | 問い、目的、背景、あなたに頼む理由、入力値、番号付き手順と必要なコマンド、省いた場合の影響、終わったら返す情報、返信例 |

問いは最初に一行で太字にする。手順・入力値・コマンドをチャットへ転載しない。
作業で秘密の値が必要なら、オーナーの端末で非表示入力して登録する手順を書く。
値をコマンド引数、履歴、JSON、HTML、チャットへ残さない。返信は「登録済み」などの結果だけにする。

### 図表は柔軟に

固定するのは依頼の必須部分だけ。判断材料や各手順には、文章・見出し・表・箇条書き・コード・SVG・リンクを自由な順序で組み合わせる。
同じカードへ複数の図や表を置け、特定の図種・枚数・レイアウトを要求しない。

- シーケンス図は主体とメッセージの順序、フロー図は分岐と流れ、構造図は包含や依存、前後比較は差を示す。
- 図の作成は利用できる図解スキル/ツールやSVGで行う。種類を限定せず、静的SVGにして `svg` ブロックから参照する。
- SVGは対応する静的構文へ整え、viewBoxと要点説明を持ち、ラベルはSVGの `text` / `tspan` を使う。HTMLラベルの `foreignObject`、script、イベント属性、外部参照、style要素は受け付けない。対応する静的SVGとして書き出す。
- ライト表示、必要なコントラスト、図の代替説明を保つ。込み入った解説は別HTMLへ切り出し、判断の正本は連絡板に保つ。
- 長いコードは折り返す。グリッドは `minmax(0,1fr)` と `min-width:0` を使い、カードの内容を `overflow:hidden` で切らない。
- 図・表は必要な領域だけ横スクロール可能にする。コピー機能なしでもコードを選択して読めるようにする。

## 最新化

1. **追加**: 保存済みの全項目・記録を確認し、最後に使用した番号より大きいQ番号を採番する。
   統合板は `Q1`、担当板は `<session-id>-Q1`。小問は `Q5-1` のように親へ結び付ける。
   提示後に問い・対象操作・条件・選択肢の意味を変える場合は、未回答の旧Qは理由付きで取り下げ、新しいQで提示する。
   回答済みの旧Qは `answered` と当時の内容・回答を保持し、後継Qとの関係を新Qの背景に記す。
   誤字修正など意味を変えない補足は同じQでよい。準備中から提示する時点で意味を固定する。
   番号は固定・再利用禁止。選択肢の既定は `1` / `2` とし、ラベルとセッション名を衝突させない。
2. **回答受領**: 対象番号と回答を照合する。「全部1」は指定された小問だけに適用し、別の質問へ広げない。
   判断が分かれる曖昧さだけ確認する。解説の要求を回答や承認として扱わない。
3. **記録化**: 同じ項目を `answered` にし、回答・受領時刻・その後の対応・必要な中継先を記録する。
   生成で一覧から外して記録へ移す。元の問い・選択肢・手順は保持し、HTMLの記録からも読めるようにする。元の項目は削除しない。提示済みQが参照する図や解説も上書きせず、変更時は別名で保存して当時の判断材料を保つ。取り下げは `withdrawn` と理由を残す。
4. **反映**: 回答の受領と作業の反映を分ける。反映が未完了なら `follow_up.state=pending`。
   回答に基づく操作の許可範囲を確認し、関連作業を処理してから `done` と対応結果へ更新する。
5. **再生成**: 検証と生成を行い、番号・一覧・カード・回答記録・更新時刻・リンクを確認する。
   重要な表示変更は実表示も確認し、短く通知する。既に受領した承認を記憶不足だけで取り直さない。

開始時に、回答を受け付ける各セッションへ板・更新担当・本スキルの回答受領と中継の運用を明示して共有する。
Q番号だけの返信で本スキルが自動発火すると保証しない。運用を共有できない場合は更新担当へ直接回答するよう案内する。

一枚のJSON/HTMLの更新担当は一つのセッションにする。別セッションはその板を直接編集せず、更新担当へ情報を渡す。
同時更新のためのlock・daemon・自動マージは実装していない。

## 複数セッションと中継

[セッション間の運用](references/coordination.md) を複数セッションの開始時・担当交代時に読む。
判断・承認・権限・優先度・セッションをまたぐ事項は統合役の板へ集約する。
担当固有の論点を担当板に置く場合、統合板からリンクする。同じ質問を両方で編集する二重管理はしない。

どのチャットで回答を受け取っても、依存する次の操作に進む前に統合役と関係担当へ中継する。
成功を確認してから `relays[].state=sent` とする。送信できなければ、受領側で未送信の引継ぎ記録と中継文を残す。更新担当が受領してから板へ `pending` を記録する。
板への書込権限も通信もない場合の手順は、セッション間の運用に従う。
利用可能で許可されたセッション間通信だけを使い、無断でメール・Chat等の外部送信を追加しない。

## 通知・開き方・検証

チャットはQ番号と一言、連絡板のリンクだけを基本にする。

```text
Q12：確認範囲の判断をお願いします。［連絡板のQ12へのリンク］
Q13：サンプル確認の手順を載せました。［連絡板のQ13へのリンク］
Q12：回答を記録し、関係担当へ共有しました。［連絡板へのリンク］
```

初回と重要な新規依頼時は、保存した最終版をOSの標準方法で開く。通常更新は通知とリンクのみ。
これは継続更新する連絡板向けの表示設定であり、html-artifactの「更新ごとに開く」既定に優先する。
ユーザーの別指定には従う。開く命令の成功と実表示検証を区別する。

初回・表示変更時はbrowser-operationsを読んでブラウザで確認する。図・表・長いコードを含む状態で、
デスクトップ、320px程度の狭い幅、200%拡大、キーボード、コピー、折りたたみ、資料リンクを確認する。
未確認の項目や失敗は明記し、WCAG準拠や自動復帰を検証なしに保証しない。

## 出す前の確認

- 目的と省いた場合の影響があり、人間に聞く必要のない確認を出していないか。
- 推奨理由と欠点、未検証・推定、回答期限と準備中の区別が見えるか。
- 一覧・カード・記録の番号が一致し、回答済みのQ番号を消していないか。
- 未反映の回答や中継待ちを、処理済みとして隠していないか。
- 手順・入力値・長いコードが切れず、チャットへ手順を流していないか。
- 図表が判断に役立ち、別資料へのリンクと戻り先が存在するか。
- 設定した用語を文章へ反映したか。コマンド・識別子へ一括置換していないか。
- 秘密・個人情報・企業固有情報・内部URLを公開物やサンプルへ混ぜていないか。
