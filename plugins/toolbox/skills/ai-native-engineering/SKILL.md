# AI-native Engineering

AIは、仕様の明確な実装・検証・移行を長時間かつ並列に進められる。人間なら大規模に見える基盤整備でも、人の関与が判断とレビューに限られるなら安いことがある。一方で、AIが作れることと作る価値があることは別で、需要を確かめていない機構は、理解・変更・運用する対象を増やす。

目的は、**プロダクトの生涯にわたる手戻り・移行・保守・並列開発の阻害・機会損失を最小にしながら、必要な品質を最短で実現すること**。最も多く作ることでも、最も少なく作ることでもない。必要な契約と品質を満たす最も単純な構成を選び、機構は実需に合わせて足す。

## 判断の軸

提案ごとに、次の5つを言葉にする。

| 軸 | 見ること |
|---|---|
| 後戻りコスト | 変更は局所か全体か。永続データ・外部API・認証境界・公開契約を持つか。旧新の併存が要るか。変更中に他の実装を止めるか。失敗するとデータ損失・権限事故・長期停止が起きるか |
| 必要性の確度 | 運用するなら避けられないか。現在の受入条件・脅威・規制に必要か。具体的な利用者とユースケースがあるか、想像か |
| AI圧縮率 | 仕様が明確で、機械的に実装・検証できるか。独立したレーンに分けられるか。人の入力なしにテストで正しさを確定できるか |
| 人間・外部依存 | 要求・優先順位・法的判断が未確定か。目視や実利用者の反応が要るか。権限者の操作・外部審査・観測期間が要るか。同時実行枠やrate limitなど実在する上限があるか |
| 利用者の体験 | 繰り返し通るコアジャーニーか。利用頻度・失敗頻度・認知負荷は高いか。暫定の操作や概念が定着しないか |

AI圧縮率が高くても、人間・外部依存が支配する工程はカレンダー上ほとんど縮まらない。圧縮率が高く依存が少ない基盤整備は、人間の感覚より大きく前倒しできる。

状態を持ち、変更半径が大きく、他の作業を長く塞ぐ決定ほど、初期に良い設計へ投資する。AIが移行コードを速く書けても、状態を安全に動かす順序、互換期間、観測期間、人の確認は消えない。

## 判断マトリクス

| 後戻りコスト | 必要性の確度 | 判断 |
|---|---|---|
| 高い | 高い | **今、正しく決めて実装する。** 人間の工数感で妥協しない。理想形は要件を最も単純に満たす形で、機構の最大化ではない |
| 高い | 不確か | **不確実性を先に潰す。** spike、契約の検証、migrationのrehearsal、将来を塞がない境界。機能全部は作らない |
| 低い | 高い | 必要な時点で実装する。独立していれば並列にする |
| 低い | 不確か | 作らない。具体的な需要が出てから足す |

## 今決めることと、今は作らないこと

前倒しするのは**契約・境界の決定**で、**機構の実装**ではない。混同すると、必要な決定を先送りしながら不要な仕組みを先に作ることになる。

| 領域 | 今決める（安く決まり、後から変えると高い） | 今は作らない（実需が出るまで待つ） |
|---|---|---|
| データ設計 | identity、所有権、制約、履歴の持ち方、削除・保持、migration/backfillの手段があること | 分散database、sharding、CQRS、汎用監査基盤 |
| API・イベント契約 | 公開する型、versioningの方針、error model、idempotencyの境界、再試行の意味 | gateway、schema registry、独自protocol層、全経路の非同期化 |
| 認証・認可 | principal、tenant・組織の境界、role/capabilityの粒度、secretの置き場所、監査の対象 | 汎用ABAC、SSO/SCIM、per-tenant鍵、常設監視 |
| インフラ | 環境の分離、設定・secretの注入経路、deploy/rollbackとbackup/restoreが実行できること | multi-region、service mesh、自作PaaS、過剰なIaCの抽象 |
| 信頼性 | failure modeの洗い出し、冪等性、再処理の入口、最低限の可観測性 | 分散trace基盤、自動修復、SLO運用一式 |
| 開発基盤 | testability、型・schemaの契約、CIの品質ゲート、local/stagingの再現性 | 独自test framework、汎用生成器、全網羅E2E |

- 左列は、現在小規模でも曖昧にしない。右列は、観測された利用・負荷・脅威が出てから足す。
- 利用が確認されていない補助画面、通知、export形式、高度な設定項目、外部連携、管理UI、性能最適化、1事例だけのplugin化は、需要を待つ。後付けでデータモデルや権限境界を壊すものは、その境界だけ先に設計する。
- 本番投入せず、架空dataで仮説だけ確かめて捨てるprototypeには、本番基盤を求めない。再現性・隔離・廃棄可能性など、仮説の検証に要る品質だけを持たせる。

## フェーズ

- **Phase 0 — 全体を設計する。** コアジャーニー、受入条件、上の表の「今決める」列を確定する。成果物は決定と契約。
- **Phase 1 — 動くものを最短で通す。** コアジャーニーをend-to-endで1本通す。契約はPhase 0のものを使い、機構は最小にする（単一database、直呼び出し、手動運用でよい）。
- **Phase 2 — 実需に合わせて足す。** 観測された利用・負荷・脅威・反応を根拠に、機構と機能を足す。Phase 1の契約の内側に収まらないなら、Phase 0の決定を見直す。

どの段の受入条件にも紐づかない仕組みは、まだ作らない。Phase 1で落とすのは機構の量と機能の幅で、コア体験の質と、テスト・データ整合性・復旧可能性は落とさない。あるべき体験や中長期に効く施策を落とす時は、どの段で回収するかを併せて示す。

## コア体験

磨くのは、利用者が価値を得るために頻繁に通るコアジャーニー。削る対象は機能の幅で、コア体験の質ではない。コアジャーニーの受入条件には、初見で操作と結果が分かること、待機・成功・空状態・部分失敗・復旧方法が明確なこと、応答性・accessibility・keyboard操作を含める。低頻度の補助機能や例外導線には、同じ密度を求めない。目視と実利用者の反応は人に依存するので、実装と並行して早く始める。

## Securityはリスクに比例させる

現在の脅威モデルに十分で、将来の強化を妨げず、後から直すと高く付く信頼境界を初期から正す。守る資産、攻撃者、到達できる経路、侵害の影響、既存の統制の不足を具体化し、導入を待った場合の移行コストと、対策自身が増やすsecret・権限・障害点・運用負荷を比べる。

- 資産やprincipalは、現在の受入条件に実在し、侵害・誤操作・取り違えで損害や説明責任が生じるものを数える。将来いるかもしれない利用者やdataは数えない。
- 対応する資産・principal・secret・到達経路があるなら、小規模でも、認証・認可、identityとownership、組織の境界、secret管理、入力と信頼の境界、安全なdefaultは落とさない。単一利用者・offline・使い捨ての環境に、存在しない境界のための機構を作らない。
- 具体的な需要・脅威・規制が無ければ、高度なABAC、未利用のSSO/SCIM、常設監視bot、SIEM連携、per-tenant鍵、全経路mTLS、service meshは待つ。リスクが低く後付けが高い場合は、機構全部ではなく、境界・schema・移行できることだけを先に確保する。

## 投機的な抽象化

抽象化は、現在確認できる変化の軸に対して行う。問いは1つ：**観測済みの差異を整理しているか、まだ存在しない差異を発明しているか。**

| 投機的 | 投機的ではない |
|---|---|
| 実装が1種類なのに、provider interfaceとplugin loaderを作る | 2つ以上の実装で確認できた差分の、共通部分を抽出する |
| 2つ目の利用者がいないのに、汎用workflow frameworkにする | 選定済みの外部SDKを薄い境界に閉じ込め、domain modelへ漏らさない |
| 単一組織の段階で、multi-tenantの機能一式を作る | migrationやAPI versioningのように、利用開始後の導入が高い変更経路を用意する |
| 設定ファイルで足りる段階で、汎用rule builder UIを作る | 認可の判定を各handlerに散らさず、検証できるpolicy境界に集める |
| 実測負荷が小さいのに、将来のscaleだけで分散構成にする | 外部への副作用にidempotency keyを設け、再試行で重複しない契約にする |

providerが未選定なら、差し替えの機構はまだ作らない。現在のユースケースが必要とするrequest/resultの契約と、外部副作用の呼び出し箇所だけを局所化し、SDKが決まった時点でその依存を境界の内側に閉じ込める。

### BASIS ラベル

機構・抽象・防御・設定の追加、またはその提案には、必要性の根拠を次の4分類で明示する。

- `BASIS: OBSERVED` — コードやテストで観測された事実、再現する不具合
- `BASIS: CURRENT-THREAT` — 現在の脅威モデル・受入条件・規制の要求
- `BASIS: REAL-DEMAND` — 実在する利用者・ユースケース
- `BASIS: SPECULATIVE` — 「将来こうなるかもしれない」という仮説だけが根拠

本節が定めるのは分類だけである。`SPECULATIVE` の処分（削除を既定とするか、保留して人の判断材料に回すか）は、このラベルを使う各スキル・工程が宣言する。分類に迷う場合は、上の表に照らす。

## 計画と見積もり

工程ごとに圧縮のされ方が違う。一律の「AIなら速い」を使わない。

| 圧縮 | 工程 |
|---|---|
| しやすい | 明確なschema・型・CRUD・変換・配線、独立したtool・test・fixture・migration script、機械的なrefactor、契約が固まった後の並列実装 |
| 中程度 | 新規性のあるarchitecture、複数systemの結合、securityのレビュー、failure modeの設計、性能の検証、状態を持つ大型migration |
| しにくい | 要求の確認と合意、UI/UXの目視と実利用者の反応、法務・規制・外部審査・契約・権限者の操作、本番でしか得られない観測期間、人が責任を持つ最終判断 |

計画の手順:

1. 受入条件と、本気で運用するかを確かめる。
2. 大きな設計判断ごとに5つの軸を評価する。
3. 後戻りコストも必要性も高い**契約・境界の決定**をPhase 0に置く。決定と、それを実現する機構の実装を、同じ項目にまとめない。
4. コアジャーニーをend-to-endで通すPhase 1と、その受入条件を定める。
5. 不確かだが後戻りが高い箇所には、実装の前半に検証のタスクを置く。
6. 圧縮しにくい人間・外部の工程を、先に依頼・予約する。回答を待つ間に、圧縮しやすいレーンを進める。
7. 実装は、依存・整合・リスク・実在する容量の制約でgraphにし、それ以外を並列のレーンに置く。人数の感覚や作業量で直列にしない。
8. 各項目に、どの段の受入条件に必要かを書く。書けない項目はPhase 2以降へ回すか、落とす。
9. 需要が未確認で、後から安く足せる機能は、外す理由と影響を示して現在のscopeから外すことを提案する。自律実行が明示されていなければ、scopeを変える前にユーザーの確認を得る。

見積もりは分けて示す。

```markdown
従来の人間主体の尺度: <比較用の作業量・期間>
AI主体の見通し:
- AI実行時間: <連続稼働・並列度・検証を含む>
- 人間関与時間: <要求、判断、レビュー、目視確認>
- カレンダー支配要因: <外部待ち、観測、承認、容量上限>
前提と実測根拠: <既知 / 未検証を区別>
```

過去の実測が無ければ、精密な倍率を作らない。作業一覧・契約の数・依存graph・使える並列枠のどれも分からない段階では、案件の類型だけからcalendar rangeを補わない。先に確かめる項目と、外部待ちを含む見積もりの式を示し、材料が揃ってからrangeを出す。

## 推奨に残す理由

読み手が同じ前提から判断し直せるだけの根拠を残す。

- 何を最適化しているか（初期の速度、総コスト、変更のしやすさ、安全性、機会損失）
- なぜ今行うか、または待つか。どの段の受入条件に必要か
- 検討した、より単純な案と、それを採らない理由
- 後戻りの時に何が動き、どの作業を止めるか
- AIで圧縮できる部分と、人間・外部依存で圧縮できない部分
- 不確かな前提と、それをいつ・どう確かめるか

## アンチパターン

| 誤り | 矯正 |
|---|---|
| 「大変なので簡易DB/APIから」「利用者1人なので認可は後」 | 後戻りコストを見積もり、運用の前に契約と境界を正す |
| 「AIなら作れるので管理UIも作る」 | 設定で足りる間は、機能を待つ |
| 「AI-nativeなので最初から全領域を作り込む」 | 契約・境界だけ先に決め、機構は実需に合わせて足す |
| より単純な案を検討せずに構成を決める | 同じ結果を出せる単純な案を1つ挙げ、採らない理由を示す |
| 段を切らずに機構から積む | Phase 0で契約を決め、Phase 1でコア導線をend-to-endに通す |
| 単純化やYAGNIを口実に、体験・migration・rollbackを落とす | 落とすのは機構の量と機能の幅に限り、回収する段を明示する |
| 「securityなので念のため全部固くする」 | 脅威モデルと後戻りコストに比例して、統制を選ぶ |
| 全作業に同じ圧縮率を掛ける。依存の無い作業を人数の感覚で直列にする | 工程を圧縮のしやすさで分け、実在する依存と容量だけを直列の理由にする |
