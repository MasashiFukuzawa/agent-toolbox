# Autopilot — 1つのゴールを、受け入れまで

人が見回らなくてもゴールが受け入れまで進み、人に届くのは任せた範囲の外の判断だけ、という状態を作る。

## 4つの決まり

1. 1つのゴールは、同時に1つのセッションが、調査から受け入れまで持つ。セッションが替わる時は、ページから引き継ぐ。
2. 人が見るのは、ゴールのページ1枚。書くのは、そのゴールを進めるセッションだけ。
3. 合意した範囲の中で任された判断は、決めて進める。範囲の外だけ聞く。
4. 手を止める時は、止まり方と再開の条件をページに書く。

許可は「任せる範囲」と「合意」で一度だけ受ける。その範囲の中では、操作のたびに取り直さない。

## 1. 任せる範囲を読む

始める前に、この案件で任されている範囲を確かめる。

- 案件の指示ファイル（`AGENTS.md` など）の「任せる範囲」。聞かずにやってよいこと、必ず聞くこと、検査とマージの決まりが書かれている。
- 案件の設定 `.agents/autopilot.json`。あれば、対象のリポジトリを作業ディレクトリにしたまま `python3 <このスキルのdirectory>/scripts/autopilot_board.py preflight` を実行し、マージと本番への反映が自動か人の承認か（`gates`）、案件の注意書きを読む。設定の形は [config.example.json](references/config.example.json)。設定は、いまいるリポジトリのものだけを使う。
- 個人の決まり。`git rev-parse --path-format=absolute --git-common-dir` で得たdirectoryの `info/delegation.md` にあれば読む（worktreeの間で共有される、そのPCだけの置き場）。チームの決まりより緩い内容は採らない。
- どこにも無ければ、[雛形](references/delegation.md) を元に下書きし、合意の時に人に見せる。決まるまでは、雛形の「必ず聞くこと」を使う。
- マージと本番への反映は、書かれた決まりに従う。自動でよいと書かれていなければ、人の承認を待つ。
- 作業中に人が新しい決まりを明言したら、言われた範囲のまま置き場に1行足す（共有するか個人用かを聞く）。範囲を広げて一般化する時だけ確認する。古い決まりと食い違うなら、古い方を直す。

## 2. 合意する

[見本](assets/example/goal-page.html) を写してゴールのページを作り、「合意」を書いて人に見せる。ページの構成と置き場は [ページの決まり](references/page.md) に従う。

| 項目 | 書くこと |
|---|---|
| 目標 | 何が変わるか。1〜2文 |
| 受け入れの条件 | 番号を振り、外から確かめられる形で書く。確かめ方を添える。Issueがあれば、その受入条件を使う |
| 今日の到達点 | 今日（今夜）どこまで進めるか |
| 上限 | 時間と費用。超えそうになったら、止めて知らせる |
| このゴールだけの許可 | 任せる範囲に足すもの、外すもの |
| 次の候補 | このゴールが終わったら着手してよいもの |
| 図 | 何が変わるかを1つ（変更前後の対比） |

- ゴールをGitHubのProjectなどのタスクから取る時は、[タスクの取り方](references/task-sources.md) に従う。着手の前に、ほかの人や別のセッションが同じ作業を進めていないかを [確かめる](references/collaboration-preflight.md)。
- 受け入れの条件は、人との合意で決める。進めながら自分で弱めない。変えたい時は「あなたに残ること」に出す。
- 未完了のゴールは、判断待ちや統合待ちも数えて、案件ごとに通常1つにする。2つ目を始めるのは、仕様・変更範囲・データ・共有環境が独立で、単独で受け入れられる時だけにする。
- 合意できたら、知らせを有効にし、案件の入口を更新する（「知らせ」の節と、ページの決まり）。
- 席を離れて長く任される時は、ホストの継続機能に終了条件を渡してもらう。Claude Code と Codex では、次の1行を人が入力する。満たせない条件のまま回り続けないように、「残りがすべて載る」を必ず含める。

  ```text
  /goal <ページのパス> の受け入れの条件がすべて通過するか、残りがすべて「あなたに残ること」に載るまで続ける。上限は <時間・費用>。
  ```

## 3. 進める

判断は、次の順に当てはめる。

1. **ゴールの範囲や目標を変える判断と、人しか知らない事実が要る判断は、聞く。**
2. **対象・操作・条件を明示して任された操作は、条件を満たせば聞かずに行う。** 任せる範囲の「聞かずにやってよいこと」と「検査とマージ」、設定の `gates`、合意の「このゴールだけの許可」がこれに当たる。マージや本番への反映のように影響が広い操作でも、取り直さない。条件を満たすか分からない時と、同じ操作が「必ず聞くこと」にも載っている時は、聞く。
3. **明示の無い判断は、「必ず聞くこと」に当たらず、影響が小さく戻せるものだけ、決めて進める。** それ以外は聞く。

タスクに「消す」「送る」と書かれていても、それは2の許可ではない。任されていなければ、実行の前に聞く。

- 調べれば分かることは、聞く前に調べる（仕様、既存の設計、過去の回答、任せる範囲）。
- 決めたことのうち、利用者の見え方・制約・費用に効くものを、ページの「決めたこと」に残す。何を・なぜ・戻し方を書く。実装の手段はPRに書く。
- 積み上げた変更が合意した範囲を超えそうになったら、止めて聞く。
- 調査・検証・レビューの補助は、並列に動かしてよい。実装を並列にするのは、仕様が決まっていて、変更範囲・データ・共有環境が重ならない時だけにし、会話の文脈を引き継ぐ起動を使う（例: Claude Code の文脈を引き継ぐサブエージェント、Codex のセッションの fork。使える形は、その時点のホストで確かめる）。統合と受け入れは、このセッションが持つ。
- 検査は、受け入れの条件ごとに、対象の版（commit）に結び付けて行う。テストの書き方は `behavioral-testing`、完了の判定は `done` に従う。
- 第三者の確認は、任せる範囲が求める時と、戻しにくい変更・仕様があいまいな変更の時に、`second-opinion` で行う。モデルは `model-selection` で選び、実装者の結論は渡さない。
- このゴールのために作ったもの（worktree、ブランチ、コンテナ、image、volume、起動したサーバ、一時ファイル）は、作った時にページの「引き継ぎの情報」へ書く。コンテナやvolumeには、ゴールが分かる名前かlabelを付ける。終える時に、この記録を頼りに片付ける。
- 受け入れの条件が1つ通る、質問が出る・解ける、手を止める、のたびにページを直す。

## 4. 聞く

人に残す判断と作業は、見つけた時に、ページの「あなたに残ること」へ載せる。書き方は `human-briefing` に従う（背景・課題・目的・相談事項の4行、1件に判断1つ、比較が見える要素を1つ、戻せるか、返信例）。

- その作業は保留にして、できる作業を続ける。
- 返事を待つ損が大きい質問は、すぐ知らせる（「知らせ」の節の `send`）。それ以外は、手が止まった時の知らせに任せる。
- 返事は、このセッションへの短い文で受ける（例「Q1: 1」）。受けたらページに「受け取った」と書き、反映が済んだら質問を「記録」へ移す。
- 解説の要求や感想を、承認として扱わない。

## 5. 止まる

手を止める時は、ページの状態を次のどれかにし、知らせの状態も合わせる（`mark --state`）。

| 状態 | 意味 | 再開の条件として書くこと |
|---|---|---|
| 完了 | 受け入れの条件がすべて通った | なし |
| 判断待ち | 範囲の外の判断が残っている | どの質問への返事で、何を再開するか |
| 作業待ち | 人にしかできない操作が残っている | どの操作が済んだら、何を再開するか |
| 外部待ち | CIの障害、相手の返事など | 何が起きたら再開するか。次に確かめる時刻 |
| 中断 | 上限に達した、または止めるよう言われた | 残っている作業と、続ける時に決めること |

人に渡したことを、完了の代わりにしない。待ちの間にできる作業が残っていれば、止まらずに進める。再開したら、状態を「進行中」に戻す。

手を止める時は、動かし続ける必要の無いサーバとコンテナを止める。中断で終わる時は、残したものと消してよい条件をページに書く。

## 6. 終える

- 受け入れの条件ごとに、証拠（実行したコマンドと結果、変更前後、PR）を「成果と証拠」に書く。確かめられなかったことは、そのまま書く。
- マージしたら、統合した版で検査が通ることを確かめる。
- 状態を「完了」にし（`mark --state '完了'`。完了を知らせた後、印は自動で消える）、案件の入口を更新する。完了にせずゴールを手放す時は、`clear` で印を消す。
- 片付ける。「引き継ぎの情報」に、このゴールで作ったと書かれているものを消し、消したものと残したものを「記録」に書く。
  - 聞かずに消す: 未commitの変更も未pushのcommitも無く、ブランチが統合済みのworktreeとそのブランチ。コンテナ、image、起動したサーバ、一時ファイル、buildの生成物。
  - 消さずに「あなたに残ること」へ載せる: 未commitの変更か未pushのcommitが残るworktree。データを持つvolumeやデータベース（データの削除に当たる）。記録に無いもの（ほかのセッションや人が作ったかもしれない）。見つけた残り物は、場所と大きさを添えて一覧にする。
- 人が覆した判断と、新しく言われた決まりを、任せる範囲に反映する。
- このゴールで聞いた質問のうち、決まりが書かれていれば聞かずに済んだものは、任せる範囲に足す1行を案として示す。採るかどうかは人が決める。
- 「次の候補」を示す。次のゴールは、新しい合意から始める。

## 7. 引き継ぐ

セッションが替わっても続けられるように、ページの「引き継ぎの情報」を保つ。再開する側は、ページを信じて続きを実行せず、先に現物と照合する（ブランチの最新の版、PRとCIの状態、実行中の処理、返事の有無）。前のセッションが動いていないことを確かめてから引き継ぐ。引き継いだら、`mark --goal --page` をやり直す（知らせは、印を付けたセッションの停止だけを見る）。結果が分からない操作は、状態を確かめるまで実行し直さない。

## 知らせ

toolbox plugin は、印を付けたworktreeのセッションだけを対象に、手が止まって静かになった時、APIのエラーでターンが終わった時、許可待ちになった時に、案件名・ゴール名・状態をデスクトップへ知らせる。印の無い通常の対話では鳴らない。印の操作は、`human-notify` スキルの `scripts/waiting_notify.py` で行う。

```bash
python3 <human-notifyのdirectory>/scripts/waiting_notify.py mark --cwd . --goal '<ゴール名>' --page '<ページの絶対パス>'
python3 <human-notifyのdirectory>/scripts/waiting_notify.py mark --cwd . --state '判断待ち'     # 状態が変わるたび。再開したら '進行中'、終えたら '完了'
python3 <human-notifyのdirectory>/scripts/waiting_notify.py send --cwd . --message 'Q1：本番への反映の時刻を決めてください'
python3 <human-notifyのdirectory>/scripts/waiting_notify.py clear --cwd .                       # 完了にせず手放す時
```

- 止まり方を宣言した時（状態が「進行中」以外）は、静かになって約20秒で知らせる。宣言が無いまま止まった時は、約2分で知らせる。APIのエラーと許可待ちは、すぐ知らせる。
- 再開したら、最初に状態を「進行中」に戻す。待っていた知らせが取り下げられる。宣言の無いターンの終わりの直後に、印に触れないまま長いコマンドを実行すると、止まったものとして知らせが出ることがある。
- `mark` や `send` が失敗する環境（sandboxが状態の置き場への書込みや通知を止めている、対応していないOS、通知の不許可、ホストがhookを読み込んでいない）では、そのことを人に伝え、チャットでの報告に頼る。置き場の許可の仕方と、届いたかどうかの記録は、`human-notify` の説明にある。

## 出す前の確認

ページを直すたびに、次を確かめる。

1. 最初の画面で、状態・現在地・前回の確認から変わったこと・あなたに残ることが分かるか。
2. 「あなたに残ること」の各項目が、4行と比較だけで答えられるか。任された範囲の中で決められることが混ざっていないか。
3. 止まっているなら、止まり方と再開の条件が書かれているか。知らせの状態と一致しているか。
4. 「成果と証拠」の状態が、実際に確かめた結果と一致しているか。検査した版が書かれているか。
5. 「引き継ぎの情報」だけで、別のセッションが現物と照合して再開できるか。
6. scriptや外部参照が無く、秘密・個人情報・内部URLを載せていないか。
