# controllerの応答性と継続監視

## 実行ループ

controllerは長時間実装・検証を原則workerまたは非同期processへ委任する。自分の現物レビューも短く区切る。各tool境界、通知受信時、次回確認期限で次を行う。

1. 人間の停止・方針変更、安全異常を優先する。新規割当てを止め、実行中の副作用は安全な停止/完走回収/引継ぎを判断する。
2. workerの質問・失敗・完了を回収する。完了通知だけで成功とせず実終了と出力を確認する。
3. 判断待ちを解消し、controllerのレビュー・修正指示を処理する。
4. 空き枠と独立作業がある場合だけ次を委任する。
5. 有用な作業がなければhost-nativeの割り込み可能waitへ入る。単に「待ちます」とfinalを返して回収を放棄しない。

初期の確認間隔は60秒を目安とする。秒単位のbusy pollingはせず、通知を主、定期照合を取りこぼし対策とする。時刻は実時計で測る。間隔はhost/rate limitに応じて変更し、確認できない最大時間を記録する。controllerを中断不能なtoolで60秒超占有する場合は、短いyield・非同期化・委任を先に検討し、不可能なら応答制約を明示する。

通知型でも期限にはtask metadataの終了状態・未処理通知を軽く照合できる。実行途中の巨大ログを読み直さない。ハンドル型では必ず記録済みhandleをread/waitする。同期型しか使えなければ常時応答性を保証せず、その制約下で直列実行する。

## 永続索引と終了前照合

repoごとの永続state領域へrun ID、task identity、Issueの所有者記録への参照、host handle、起動時刻、次回確認期限、出力先、待ち条件を残す。controllerが単一writerとなる。task詳細をコピーした第二の台帳や独自状態databaseは作らない。

索引は復旧の入口であり、生存や完了の証拠ではない。期限および終了前に、ホストのtask一覧・記録済みhandleのstatus/read・未処理messageから実状態を確認する。自己申告JSONだけを再検査して照合済みにしない。

- 実行中ならhost-native wait/readを使う。
- 終了済みなら成功・失敗とも出力を回収し、未処理の質問・レビュー・修正を処理する。
- 外部待ちなら、何の回答が必要か、独立作業が残るか、再開条件を記録する。
- paused/stoppedでも実行中・未回収・質問を把握し、停止指示に反する新規作業はせず安全な回収/引継ぎを行う。
- 索引とhostが矛盾すれば新規起動より照合を先にする。状態不明を成功や終了に丸めない。

## ターン終了後の保証範囲

未回収・実行中を残してターンを終了する場合、host-nativeの通知による再呼出し、または登録済みの定期再開機構が必要。登録ID・次回時刻・対象runを索引から辿れるようにする。controllerが止まった後、スキルの文章だけでは起こせない。

外部監視を接続する場合、controller所有者のlease/生存確認で二重起動を防ぎ、停止・一時停止・予算上限を尊重する。監視からmerge/deploy/worker再実行を直接行わない。本pluginは常駐daemonやhost固有の自動再開adapterを同梱していない。無い環境では現在turn内のwaitを維持し、終了が必要なら手動再開条件と制約を報告する。

compaction後は正確なrun索引とIssueのcontroller-run記録を照合し、実process/host handleを確認してから回収する。停止したと思い込んで新規起動しない。無出力や期限超過だけでkill・再試行しない。
